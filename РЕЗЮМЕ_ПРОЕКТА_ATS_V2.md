## 1. Паспорт проекта

| | |
|---|---|
| **Что это** | Платформа исходящего обзвона (call-центр) для малого/среднего бизнеса: кампании с автодозвоном, ИИ-квалификация абонентов, перевод на оператора (ACD), защита Caller ID от антиспама, отчёты, записи разговоров, интеграции. |
| **Ветка разработки** | `arena/01a072c1-ats` (Pull Request №1) |
| **Стек** | Python 3.10+ (только стандартная библиотека), SQLite (WAL), один HTML-файл интерфейса, без внешних БД/Redis и npm-сборок |
| **Данные** | папка `data_v2/` (БД, записи разговоров, CRM-выгрузка, авто-бэкапы) |
| **Запуск** | `python -m app.run` → UI на `http://localhost:9124` |
| **Тесты** | **29/29 проходят** (`python -m unittest discover -s tests`) |
| **Состав кода** | `app/` — ~3350 строк Python: engine, api, server, db, telephony, security, agent, numbers, events, asterisk, crm, config, run |

Один процесс = HTTP-сервер + UI + REST API v2 + SSE-поток + поток-диспетчер звонков + SQLite. Внешние зависимости только по выбору: телефония-провайдер, LLM API, CRM-вебхук.

## 2. Как работает приложение (механика)

### 2.1. Общая схема

```
Браузеры (админ, операторы)
        │  HTTP / SSE (события в реальном времени)
        ▼
app/server.py  ──►  app/api.py  (REST API v2, авторизация, роли)
        │
        ▼
app/engine.py — поток-диспетчер, цикл раз в секунду:
   1) разобрать события провайдера (очередь)
   2) распределить новые звонки (активные кампании → каналы → номера пула)
   3) watchdog «зависших» звонков
        │
        ▼
app/telephony.py (провайдер) ──► sim (имитация) | UIS Call API | Asterisk AMI
app/agent.py     (ИИ-агент)   ──► сценарный бот (L1) | LLM-диалог (L2, опционально)
app/crm.py       (CRM)        ──► csv-выгрузка | Bitrix24 вебхук
app/db.py        (SQLite)     ──► вся база + миграции + авто-сиды
app/numbers.py   (пул номеров)──► лимиты/день, «остывание», карантин, веса
app/events.py    (SSE)        ──► подписки браузеров на события
```

### 2.2. Жизненный цикл одного звонка

1. **Кампания.** Админ создаёт кампанию: сценарий (`message` — озвучка,
   `agent` — ИИ-агент, `operator` — сразу на оператора), шаблон текста,
   расписание (окно часов + дни недели), попытки на контакт, лимит каналов,
   «умные интервалы повторов». Контакты добавляются в список кампании
   (`campaign_items`, статус `queued`).

2. **Распределитель** (каждую секунду, пока кампания `running`):
   - проверяет рабочее окно расписания;
   - проверяет свободные каналы (глобальный лимит и лимит кампании);
   - берёт следующий `queued`-элемент, у которого наступило `next_attempt_at`;
   - **без звонка** отсекает: нет согласия → `blocked_no_consent`; в чёрном
     списке → `blacklisted`;
   - берёт номер из пула Caller ID (учёт лимитов/остывания);
   - создаёт запись `calls` (статус `dialing`) и вызывает `provider.dial()`.

3. **Провайдер** доставляет звонок:
   - **sim** — имитирует: исход по вероятностям (45 % человек, 10 % автоответчик,
     15 % занято, 20 % нет ответа, 8 % сбой, 2 % блок) либо по заданному вручную
     сценарию для конкретного номера;
   - **UIS** — HTTP Call API в облако «МегаФон Ювис» (Bearer-токен), статусы
     возвращаются **вебхуками** на `POST /api/v2/webhooks/uis`;
   - **Asterisk AMI** — через свою АТС (AMI-клиент с автопереподключением),
     события приходят от PBX.
   События кладутся в очередь движка и обрабатываются в том же цикле.

4. **Абонент ответил** — развилка по сценарию:
   ```
   ответил человек
     ├─ message  → проигрывается текст → done_ok («сообщение доставлено»)
     ├─ agent    → ИИ-агент:
     │     ├─ без LLM: сценарный диалог «вопрос — ответ 1/2» (дерево в шаблоне)
     │     ├─ с LLM: свободный диалог по критерию квалификации
     │     ├─ квалифицирован + «переводить на оператора» → ACD-очередь
     │     └─ иначе → done_agent / qualified_no → CRM
     └─ operator → сразу в ACD-очередь
   автоответчик → machine → перезвон позже
   занято/нет ответа → busy / no_answer → перезвон позже
   ```

5. **ACD (очередь на оператора).** Звонок ждёт оператора с таймером
   (`acd_wait_timeout_sec`, по умолчанию 60 с):
   - оператор нажал «Принять» → соединение, оператор `busy`, идёт разговор;
     «Завершить разговор» → `operator_ok`, оператор снова `free`;
   - никто не принял → `no_operator` + в CRM уходит **задача «перезвонить»**.
   Оператору в браузере приходит звук + системное уведомление о новом звонке.

6. **Итог попытки и автодозвон** (`_finish_attempt`):
   - успех (`done_ok` / `operator_ok` / `done_agent`) → элемент завершён;
   - «перезваниваемые» причины и попытки не исчерпаны → элемент снова `queued`,
     в `next_attempt_at` ставится время повтора;
   - интервал повтора: сначала **retry_map** кампании (`{"busy":5, ...}` —
     минуты по причинам), иначе базовый интервал с **эскалацией**
     (15 мин после 1-й попытки, 30 — после 2-й, …);
   - попытки исчерпаны → `exhausted`.
   Каждая попытка пишется в таблицу `attempts` (для точной аналитики).

7. **CRM и отчёты.** Финальные звонки уходят в CRM (`csv`-файл в
   `data_v2/crm_out/` или вебхук Bitrix24). Все звонки/попытки — в БД, из них
   строятся журнал, отчёты за период (пресеты и «с — по», до 366 дней,
   динамика по дням/неделям), экспорт CSV.

### 2.3. Пул номеров — защита Caller ID от антиспама

- суточный лимит звонков на номер (счётчик сбрасывается в полночь);
- «остывание»: после звонка номер N секунд недоступен (по умолчанию 5 с);
- **автокарантин**: при жалобах абонентов (порог в настройках) номер уходит
  в карантин; вручную — кнопкой в UI;
- веса: номера с большим весом используются чаще;
- если пул исчерпан/остывает — распределитель ждёт следующего тика, без
  «пачек» звонков.

### 2.4. ИИ-агент (два уровня)

- **L1 — сценарный (работает сейчас, без внешних ключей):** дерево вопросов
  из шаблона; распознавание ответов 1/2 (и слов «да/нет/интересует…»);
  протокол сессии сохраняется в `agent_sessions`.
- **L2 — LLM (включается настройкой):** OpenAI-совместимый клиент
  (`base_url` + модель + ключ из env `ATS_LLM_KEY`); свободный диалог по
  критерию квалификации кампании; ответ парсится в структурированный
  результат `{qualified, summary, ...}`.
  Если LLM недоступен — агент автоматически работает по сценарию (L1).

### 2.5. Watchdog и надёжность

- раз в N минут проверяет звонки, «зависшие» в `dialing/agent/wait_operator`
  дольше нормы (провайдер не прислал финал) — принудительно закрывает их
  (`failed`/`timeout`), чтобы каналы и операторы не залипали;
- авто-бэкап SQLite при каждом старте (последние 12, WAL-safe через
  `sqlite3 backup`);
- если провайдер недоступен — движок откатывается на `sim` и продолжает работу;
- клиент AMI сам переподключается при обрыве.

### 2.6. Роли и безопасность

- **admin** — всё; **operator** — ACD, статусы, база контактов, свой пароль;
- вход: PBKDF2-хэши паролей + соль; токены сессий; защита от перебора
  (5 ошибок за 10 минут → блокировка 5 минут, HTTP 429);
- `need_auth` сверяет пользователя с БД на каждом запросе: отключённый
  (`active=0`) или удалённый вылетает мгновенно; роль в живой сессии
  обновляется; сброс пароля завершает чужие сессии;
- «нельзя отключить/удалить самого себя и последнего администратора»;
- телефоны валидируются (E.164: 10–15 цифр), импорт даёт отчёт по ошибкам.

### 2.7. Реальное время (SSE)

Движок/API публикуют события `call/item/acd/campaign/agent`; браузеры держат
SSE-поток `GET /api/v2/events?token=…`. Без перезагрузки страницы обновляются
очередь ACD, панель разговора, журнал, счётчики, оператору приходит
уведомление+звук.

## 4. Ключевые технические методы (шпаргалка)

- **Архитектура**: один процесс; поток-диспетчер с циклом 1 с; очередь событий
  провайдера → единая обработка (`drain_events → handle_event`).
- **Хранение**: SQLite (WAL) + миграции колонок; авто-бэкапы при старте.
- **Реальное время**: SSE-поток на событиях публикации (pub/sub).
- **Безопасность**: PBKDF2 + соль, токены сессий, rate-limit входа, проверка
  активной роли на каждом запросе, запрет само-отключения.
- **Антиспам-звонки**: пул Caller ID (лимиты/день, остывание, карантин, веса).
- **Автодозвон**: retry_map по причинам + эскалация интервала; watchdog.
- **ИИ-агент**: L1 сценарный (дерево + нормализация ответов), L2 LLM
  (OpenAI-совместимый, ключ из env), graceful fallback на L1.
- **Телефония**: общий интерфейс провайдера (dial/hangup/события); адаптеры
  sim / UIS Call API / Asterisk AMI; авто-откат на sim при недоступности.
- **CRM**: интерфейс драйвера → csv (файлы) / bitrix24 (вебхук).
- **Тестирование**: 29 unittest (ядро, пул номеров, E2E-цикл звонка, HTTP API,
  AMI-протокол, UIS-вебхуки, ACD-timeout, чистый старт, clean-demo), плюс
  живой e2e-прогон полного цикла на sim.

## 6. Что нужно для запуска

### 6.1. Уже сейчас, локально (бесплатно, без договоров)

Запуск на своём компьютере (`python -m app.run`) — вся функциональность на
sim. Подходит для: обучения, отладки сценариев, ведения базы, подготовки
кампаний, проверки работы операторов. **Телефон не звонит** — sim имитирует.

### 6.2. Тест звонка на свой номер — через UIS («МегаФон Ювис»)

Это самый короткий путь к «живому звонку» без своего оборудования. Пошагово:

1. **Получить доступ у UIS** (запросить подключение Call API / «Ювис»):
   нужны `api_url` (базовый адрес API), `api_key` (токен авторизации),
   **номер Caller ID** (с него пойдёт звонок на ваш телефон), документацию
   по схеме вебхуков (уточнить названия полей статусов).
2. **Вписать в ATS**: «Настройки → Провайдеры и интеграции» → блок `uis`:
   `api_url`, `api_key`, при необходимости `endpoints.dial`/`endpoints.hangup`
   (по умолчанию код шлёт `POST {api_url}/call/outgoing` и
   `{api_url}/call/hangup` с телом `{call_id,to,from,text,flow}` и заголовком
   `Authorization: Bearer {api_key}`), `webhook_secret`.
3. **Настроить вебхук статусов**: UIS шлёт статусы на
   `POST /api/v2/webhooks/uis` (разбор готов: ring/answered/human/done/busy/…;
   опциональный секрет — заголовок `X-UIS-Secret`). Для локального теста
   адрес должен быть доступен из интернета → временный **HTTPS-туннель**
   (ngrok / Cloudflare Tunnel) на `localhost:9124`; адрес вебхука —
   `https://ваш-туннель/api/v2/webhooks/uis`.
4. **Добавить номер** Caller ID в «Пул номеров» (провайдер `uis`).
5. **Тест**: кампания «позвонить моему номеру» (сценарий `message` или
   `agent`) → запуск → ваш телефон звонит, вы слышите бота/агента, жмёте
   1/2; в журнале и отчёте видите результат.
6. **Сверка схемы**: адаптер UIS написан «в общем виде»; точные пути и JSON
   UIS уточняются по документации после получения доступа — при необходимости
   подгоняем (1 вечер).

> Важно: исходящий вызов с компьютера уйдёт через облако UIS; для статусов
> нужен вебхук (см. п.3). Asterisk-вариант (своя АТС) вебхуков не требует —
> подходит, если в офисе есть PBX с SIP-транком.

### 6.3. Продакшен (когда решите работать «на постоянку»)

Кратко (полная пошаговая инструкция — в `ДЕПЛОЙ_НА_СЕРВЕР.md`):
- **Сервер**: Linux VPS (Ubuntu 24.04, 1 vCPU / 1 ГБ RAM), код — в
  `/opt/ats/app`, данные — в `/var/lib/ats`;
- **Служба**: systemd unit (автозапуск, `Restart=always`);
- **Домен + HTTPS**: nginx + Let's Encrypt. HTTPS обязателен для браузерных
  уведомлений операторов и вебхука UIS;
- **Бэкапы**: авто-бэкап БД при старте + внешний ежедневный архив (cron);
- **Обновления**: `git pull` + `systemctl restart ats` (данные не трогаются).

### 6.4. Что осталось внешнего (вне кода)

1. **Договор и доступ UIS (или Asterisk)** — главный блокер для реальных звонков.
2. **Свой номер/номера** Caller ID (у UIS).
3. **Сервер** (для 24/7) + **домен/HTTPS**.
4. Опционально: ключ **LLM** (свободный диалог агента), вебхук **Bitrix24**.

## 7. Ограничения и честные замечания

- **UIS-адаптер** требует сверки с реальной документацией UIS (пути/поля) —
  это нормальный шаг интеграции при получении доступа.
- **Агент с LLM**: свободный диалог включится после выбора ASR/TTS/LLM-стека
  и ключа; без него агент работает по сценарию (кнопки 1/2).
- **Браузерные уведомления** операторов работают только по HTTPS (или
  localhost); звук работает и по `http://IP` после первого клика.
- **Один ПК/процесс** = одна точка отказа; для постоянной работы — сервер.
- При переносе базы на сервер не забудьте `--clean-demo`, если в базе были
  демо-записи.
