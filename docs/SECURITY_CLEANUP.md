## 2. Сделать сегодня, не дожидаясь конца настройки

Пункты не мешают конфигурации, а снижают уже существующий риск.

```bash
# 1) сменить пароль админа АТС (UI → Настройки → Пользователи; или впервые входим и меняем)
curl -s -X POST http://127.0.0.1:9124/api/v2/users/save -H "X-Ats-Token: $ATS_TOKEN" \
  -H 'Content-Type: application/json' -d '{"login":"admin","password":"НОВЫЙ_ПАРОЛЬ"}'

# 2) убедиться, что файл с паролем не лежит в папке репозитория на сервере
sudo ls -l /opt/ats/app/data_v2/ 2>/dev/null || echo "data_v2 на сервере нет — ок"

# 3) если решите, что репозиторий не должен быть публичным (рекомендую):
gh repo edit sentinel11-11/ATS --visibility private
```

Смена пароля в UI тоже подходит — главное, что `REDACTED-ROTATED` из `data_v2/initial_credentials.txt`
уже виден в сети, и его нельзя «оставить до конца настройки».

Если в UI войти не удалось (пароль потерян, или после нескольких неудач логин заблокирован —
`too_many_attempts`), сбросьте пароль с консоли того же сервера, скрытым вводом:

```bash
sudo -u ats ATS_DATA_DIR=/var/lib/ats /opt/ats/app/venv/bin/python -m app.run --set-password admin
sudo systemctl restart ats      # счётчик неудачных входов живёт в памяти процесса
```

Спросит пароль один раз, скрыто; меньше 6 символов не примет. Форма с двумя аргументами
(`--set-password admin 'пароль'`) тоже есть, но так пароль попадает в историю shell и в вывод
`ps` — оставляйте её для автоматизации. Проверить результат — тем же `ats-token.sh` или
`POST /api/v2/auth/login`; убедитесь, что в истории ничего не осталось:
`history | grep -c password`.

Если SIP-пароль регистрации попадал в терминал без маскировки (старая версия `--print`
печатала его открытым текстом, и значение могло оказаться в скриншоте/логе чата) — это
тоже пароль «засвеченный»: попросите Мультиком выпустить новый (для них это одна правка,
у нас — перезапуск `--dry-run`-проверки и `module reload`), и заодно смените пароль AMI:
`AMIPASS=$(openssl rand -hex 24) sudo -E ./deploy/asterisk/install-multicom-trunk.sh --ami
--ats` + `systemctl restart ats`. Новые версии скрипта маскируют `password=` в `--print`
и в `--check`; полное значение только по `--reveal`.

Открытый 5060 — не гипотеза, а факт из лога: при выключенном `ufw` на транспорт уже приходят
чужие `REGISTER` (в `messages.log` — `No matching endpoint found` с адресов вида
`45.61.184.132`). С заведённым trunk-endpoint'ом это прямой риск счетов, поэтому порядок
`ufw allow OpenSSH` → `allow from 192.0.2.0/21 …` → `ufw enable` — из шага 13
`docs/MULTICOM_SETUP_STEPS.md`, а не «когда-нибудь». Второй открытый порт — сама АТС. Значение по умолчанию в `app/config.py` —
`HOST_DEFAULT = "0.0.0.0"`, приоритет такой: `--host` → `ATS_HOST` → `settings.host` →
умолчание, то есть без явного `ATS_HOST` HTTP-интерфейс и REST API торчат наружу без TLS.
Проверьте, как сейчас: `ss -lntp | grep 9124`. Варианты, по возрастанию правильности:

```bash
sudo ufw deny 9124 && sudo ufw allow from 10.0.0.0/24 to any port 9124 proto tcp   # только своя сеть
# либо вообще убрать наружу и ходить туннелем:
printf 'ATS_HOST=127.0.0.1\n' | sudo tee -a /etc/ats/ats.env && sudo systemctl restart ats
# ssh -N -L 9124:127.0.0.1:9125 root@хост   (порт берите из ss -lntp)
```

Если нужен публичный доступ — тогда обратный прокси с TLS (certbot) и логированием, а токен
всегда в заголовке `X-Ats-Token`, а не в `?token=`: адрес запроса попадает в access-логи
прокси и в историю браузера. AMI при этом остаётся закрытым: `permit = 127.0.0.1` в
`manager-ats.conf` — так и задумано.

## 2а. Сессии и токены API (что изменилось)

Токены `/api/v2/auth/login` раньше жили только в словаре процесса (`security.SESSIONS`):
любой `systemctl restart ats` выкидывал UI из сессии и обнулял `ATS_TOKEN`, с которым
работают `install-multicom-trunk.sh --ats/--numbers` и `deploy/attach_recordings.py`.
Теперь сессии в таблице `sessions` (срок `SESSION_TTL` = 8 ч, скользящий, продление не чаще
раза в 5 минут), а в БД попадает только `SHA-256(token)`: дамп `/var/lib/ats/ats.db` и
резервные копии `deploy/backup.sh` не выдают живых токенов доступа. Что с этим связано:

- `drop_token` (logout) и `drop_sessions_for` (смена/сброс пароля, деактивация) удаляют и
  строку в БД — «разлогинить всё» по-прежнему значит `sqlite3 /var/lib/ats/ats.db
  'DELETE FROM sessions'` плюс `systemctl restart ats`, если нужен и сброс `_LOGIN_ATTEMPTS`;
- если кто-то подозревает утечку токена (scp/чаты/логи прокси) — достаточно
  `DELETE FROM sessions WHERE login='admin'`, пароли пользователей это не трогает;
- БД без таблиц/недоступна — аутентификация деградирует в память, а не падает (проверено
  тестом), так что рестарт из-за `auth_required` делать не нужно.

## 4. Про историю коммитов (важно)

`git rm` и новые коммиты **не стирают** старые: данные письма и `REDACTED-ROTATED` останутся
доступны по SHA в ветках `arena/*`, пока существуют сами ветки (а после удаления ветки —
до сборки мусора на стороне GitHub; кэши и форки не гарантированно).

Варианты, по возрастанию радикальности:

1. **Ничего не переписываем.** Accept: пароль адмена уже сменён, SIP-пароль и AMI-пароль в
   git никогда не попадали, в `main` конфиденциального нет. Остаточный риск — логин `00000000`
   и список номеров в истории `arena/*`.
2. **Приватный репозиторий** (`gh repo edit --visibility private`) + удалить ветки
   `arena/01a0cdee-ats`, `arena/01a072c1-ats` после слияния: старые коммиты перестают быть
   публично доступны. Заодно запросить GC в поддержку GitHub, если принципиально.
3. **Переписать историю** `git filter-repo --replace-text …` и `git push --force` по
   arena-веткам. Делать только если репозиторий останется публичным: это ломает все
   клоны (переклон обязательный), поэтому только вместе с финальным слиянием в `main`.

Решение по п.3/п.4 — за заказчиком; я ничего не переписываю без явной команды.

## 5. Чего при чистке делать нельзя

* не трогать `docs/MULTICOM_SIP_CONNECT.md` целиком: там инструкция, по которой живём; вычищаются
  только конкретные значения;
* не удалять `deploy/ats.env.example` — это шаблон без секретов (все значения закомментированы);
* не «чистить» историю `git filter-branch` на лету, пока сервер работает с этими ветками;
* не выполнять `git clean -fdx` в `/opt/ats/app` — вместе с локальным мусором удалит
  `venv/`, `data_v2/` и всё, что сервер нагенерировал сам.
