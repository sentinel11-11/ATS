# Готовность АТС к продаже: мультиарендность, масштабируемость, тарифы

Аудит по фактическому коду на коммите `54366fb` (ветка `arena/01a0cdee-ats`). Команды
повторной проверки приведены в конце (§6) — цифры из них, а не из головы.

## 1. Вердикт одной строкой

**Продукт сейчас — single-tenant: один инстанс = один клиент со своими пользователями.**
Роли и разграничение доступа есть, «много аккаунтов с разными данными в одной базе» — нет.
Продавать подписку можно уже сегодня по модели «отдельный инстанс на клиента» (§4, ступень 0);
полноценный SaaS с общей базой — это ступень 2 со сроком 2–3 месяца.

## 2. Что показано кодом (блокеры)

| Слой | Факт из кода | Следствие |
|---|---|---|
| Конфигурация | `settings` — одна строка: `CREATE TABLE settings(id INTEGER PRIMARY KEY CHECK (id = 1), data TEXT)` (`app/db.py:333`) | один `provider`, один Asterisk-транк, один токен amoCRM, один `max_channels` на весь инстанс. «Разные клиенты → разные АТС-провайдеры» внутри одной БД невозможно в принципе |
| Изоляция данных | в 24 таблицах схемы нет ни одного `tenant_id`/`account_id`/`org_id` (`grep` по `app/db.py`) | контакты, кампании, журнал, номера, blacklist, записи — общие. Разделить нельзя даже фильтром |
| Пользователи | `users.login TEXT UNIQUE`, ролей ровно две: `admin`/`operator` (`app/api.py:1454`); `need_auth(headers, role)` сверяет равенство роли (`app/api.py:91-104`) | логин уникален глобально (два клиента не заведут по «ivanov»); ACL на объекты отсутствует: любой admin видит всё инстанса |
| Сессии | `SESSIONS = {}` в памяти процесса, `SESSION_TTL = 8*3600` (`app/security.py:8-9`) | рестарт выбрасывает всех вошедших; два приложения за балансировщиком не работают (токен живёт в одном процессе); «разоприть» пользователя можно только в его же процессе |
| Хранилище | SQLite, одно соединение на процесс (`check_same_thread=False`) + `RLock` на все запросы, `journal_mode=WAL`, `busy_timeout=5000` (`app/db.py:15-22`) | писать много потоков можно, но сериализованно; несколько процессов на одном файле — гонка на read-modify-write настроек; горизонтального масштабирования нет |
| Движок | один фоновый поток, тик ≈1.0 с (`time.sleep(0.3 if config.FAST else 1.0)`), `max_channels` по умолчанию 3, переопределение на кампании (`app/engine.py:102,1303-1313`) | потолок — десятки одновременных линий на инстанс (30–50 комфортно), не тысячи |
| AMI | один TCP-коннект к Asterisk под `RLock` (`app/asterisk.py::AMIClient`, `AsteriskAmiProvider._lock`) | `Originate`/действия идут последовательно; при сотнях каналов нужен пул соединений AMI |
| Транспорт API | `ThreadingHTTPServer` без TLS; `?token=` принимается для SSE (`app/server.py:206`, `app/api.py:118,124`) | наружу только через reverse-proxy (nginx) c TLS; токен в query попадает в access-логи |
| Тарификация | планов/подписок/квот нет: ни `plans`, ни `subscriptions`, ни счётчиков минут | «продажа подписки» требует либо внешней биллинговой системы, либо §4 ступень 2 |
| Мультиинстанс на одном Asterisk | входящие отсекаются по `inbound_contexts` и префиксу канала `{tech}/{trunk}` (`app/telephony.py:558-567`); `channel_pattern` — только исходящий шаблон набора (`app/telephony.py:404-417`) | два инстанса с одним `ami.trunk=mcm` и `from-mcm` **примут один и тот же входящий звонок дважды**. Лечится отдельным pjsip-endpoint'ом на клиента (см. §4) |

Что уже на стороне «можно продавать» (не выдумано, работает):

* `ATS_DATA_DIR` / `ATS_DB` / `ATS_PORT` из окружения и флаги `--host/--port/--provider`
  (`app/config.py:9-10`, `app/run.py:78-91`) → инстанс на клиента = каталог + юнит;
* CLI без UI: `--set-password LOGIN PAROL`, `--list-users`, `--init-only`, `--clean-demo`
  — онбординг и смена пароля админа автоматизируются;
* `audit_logs` (кто, что, откуда, `ip_address`) — «журнал для клиента» уже есть;
* защита от перебора логина: `_login_allowed`/`_login_fail` → `429 too_many_attempts` +
  `retry_after_sec` (`app/api.py:29-43,131-134`), пароли — PBKDF2-SHA256, 120 000 итераций,
  соль на пользователя (`app/security.py:21-27`);
* клиентоориентированные лимиты, которые легко продать как тарифные «пакеты»:
  `max_channels`, `daily_limit` номера, `line_cooldown_sec`, `retry_max`/`retry_delay_min`,
  тихие часы `window_start/window_end/window_days`, карантин по жалобам
  (`auto_quarantine_on_complaints`), `consent_required`, чёрный список;
* fail-closed по секретам (любой ключ в UI/API — `********`), маскирование и в `health/details`;
* `deploy/backup.sh`, `deploy/check.sh`, `deploy/update.sh --rollback` — хозяйственный контур;
* интеграции с CRM — per-instance (`amocrm`, `bitrix24`), то есть «у каждого клиента своя CRM» —
  нормальная ситуация, а не ограничение.

## 3. Что нужно менять, если цель — один инстанс на много клиентов (SaaS)

Порядок = Recommended, не «всё сразу»:

1. **Ключ аренды во всех таблицах.** `tenant_id INTEGER NOT NULL REFERENCES tenants(id)` в
   `contacts, numbers, campaigns, campaign_items, calls, operators, blacklist, templates,
   databases, events, provider_events, attempts, agent_sessions, audit_logs`; индекс
   `(tenant_id, …)`; **единая точка фильтра** — обёртка над `db.q/fetch` с обязательным
   `tenant_id` из сессии, иначе 500 (иначе рано или поздно забудете `WHERE` в одном роуте).
   Оценка: самая дорогая часть, ~150 правок запросов + тесты на «не вижу чужое».
2. **`settings` → per-tenant.** Снять `CHECK (id=1)`, добавить `tenant_id`, миграция текущей
   строки в `tenant_id=1`. Провайдер, транк, `max_channels`, ключи CRM — от клиента.
3. **Сессии в БД** (таблица `sessions(token_hash, user_id, tenant_id, expires, ip)`) +
   инвалидация при смене пароля (`drop_sessions_for` уже есть, но чинит только свой процесс).
   Это же открывает путь к нескольким процессам за nginx.
4. **Роли.** Третья роль `tenant_admin` (управляет своими пользователями, кампаниями, номерами,
   НЕ трогает `provider`/`billing`) и `superadmin` (платформа). Сегодня развилка
   `if sess["role"] != "admin"` встречается в `app/api.py` 21 раз — её надо превратить в
   `require("…")` с матрицей прав, иначе рост числа проверок станет лотереей.
5. **Хранилище: Postgres** (нужен драйвер — текущий «stdlib-only» ломается, это осознанный
   выбор), `asyncpg`/`psycopg3`, пул соединений; SQLite оставить для демо/стенда.
   Миграции сейчас — ручные `ALTER TABLE` в `app/db.py:459-461`, при 24+ таблицах и tenant-ключе
   это надо заменить версионированным миграйтером (`schema_version` + каталог `migrations/`).
6. **Движок на много арендаторов.** Один поток на 3 канала — ок; на 50 клиентов — нет:
   планировщик по `tenant_id` (справедливая очередь, а не head-of-line), отдельный AMI-клиент
   (или ARI/пул соединений) на клиента, `max_channels` как сумма по аренды + «глобальная»
   защита транка оператора. Тик 1 с → реальное время дозвона ±1 с, для обзвона приемлемо.
7. **Биллинг/квоты.** Таблицы `plans`, `subscriptions(tenant_id, plan, status, until)`,
   `usage_counters(tenant_id, day, calls, minutes, records_mb)`; мягкий лимит (уведомление) и
   жёсткий (движок не берёт кампании в работу: `campaign.active=0` + причина). Интеграция с
   эквайрингом — отдельный модуль, в ядро не тащим.
8. **Транспорт/безопасность уровня «публично».** nginx + TLS (Let's Encrypt), HSTS; отказаться
   от `?token=` кроме SSE (там — короткоживущий подписанный one-time токен); rate limit не только
   на `/auth/login`, но и на POST-роуты (сейчас limiter только для логина); `Proxy-Protocol`/
   `X-Forwarded-For` при доверии конкретному прокси, иначе `audit_logs.ip_address` врёт;
   CSP/`SameSite` для UI; секреты клиентов — env-файл на tenant или Vault, не `ats.db`.
9. **Разделение Asterisk.** На клиента: свой `transport`/`endpoint`/`aor` (имя = `mcm-t<id>`),
   свой контекст `ats-out-t<id>` и `from-mcm-t<id>`, свой AMI-пользователь с `permit=127.0.0.1`
   и `read/write` только своих каналов, свой каталог записей `/var/spool/asterisk/monitor/t<id>`
   (иначе `attach_recordings.py` притянет чужую запись к чужому `ATS_CALL_ID`).
   Это **обязательное** условие и для ступени 0: изоляция на уровне Asterisk дешевле, чем на уровне БД.
10. **Наблюдаемость.** Сейчас — логи процесса + `journalctl -u ats` + `/api/v2/health*`.
    Для продаж: Prometheus-метрики (очереди, каналы, ошибки провайдера, лаг тика), `/metrics`
    под отдельным токеном, алерты на `provider=ami` отвал и на 429.

## 4. Дорожная карта продажи: три ступени

### Ступень 0 — «приватный инстанс на клиента» (0 строк кода, 1–2 дня на автоматизацию)

Модель: клиент платит за инстанс (VM/контейнер), обновления — общий git-репозиторий.
Работает уже сегодня, с текущими ограничениями SQLite и одного движка, и это нормально
для 10–30 клиентов.

Нужно дописать (инфраструктура, не ядро):

* `deploy/provision-tenant.sh <код_клиента>`: создать `/var/lib/ats/<c>`, юнит из шаблона
  `ats@<c>.service` (`Environment=ATS_DATA_DIR=/var/lib/ats/<c>`, `--port 91<nn>`),
  логин `admin` с выданным паролем (`--set-password`), nginx-location на поддомен,
  `deploy/backup.sh` в cron, `deploy/check.sh` в cron;
* рендер Asterisk-конфига на клиента: `pjsip-<c>.conf` (endpoint `mcm-<c>`, контексты
  `ats-out-<c>`/`from-mcm-<c>`) — по образцу `deploy/asterisk/pjsip-multicom.conf`, и
  `install-multicom-trunk.sh` с `MCM_TRUNK=mcm-<c>`; в настройках АТС клиента
  `ami.trunk=mcm-<c>`, `context=ats-out-<c>`, `inbound_contexts=from-mcm-<c>,ats-in-<c>`;
* «витрина» для себя: список клиентов и их портов/доменов (файл + `deploy/check.sh --all`).

Что честно сказать клиенту на этой ступени: один сервер = один клиент; при отказе Asterisk
страдает только он; миграция данных — импорт CSV/XLSX + выгрузка (готового экспорта «всего
профиля» нет, это доработка ~1 день, если потребуется перенос между инстансами).

### Ступень 1 — «много клиентов на одной машине, раздельные базы» (2–4 недели)

Тот же single-tenant код, но:

* юнит-шаблон `ats@%i`, каталоги `data/tenants/<c>`, общий nginx с маршрутизацией по
  поддомену → порту;
* токены в БД (п.3 из §3 — он нужен, чтобы рестарт одного клиента не выкидывал всех, и чтобы
  держать 10+ процессов без памяти на каждый);
* **обязательная** изоляция Asterisk (п.9 из §3) и каталогов записей;
* общий `update.sh`/`check.sh --all`/`backup.sh --all`, лимит на число процессов,
  systemd `CPUQuota=`/`MemoryMax=` на юнит (иначе 10 клиентов делят один ядро без справедливости);
* агрегированный мониторинг и единый журнал (`journalctl -u ats@.service` + `tenant_id` в имени юнита).

Риск: «масштабирование копированием» — каждый клиент добавляет процесс и Asterisk-нагрузку;
это нормально до десятков клиентов и плохо для сотен.

### Ступень 2 — «настоящий SaaS» (2–3 месяца, 1–2 разработчика)

§3 пункты 1–10, плюс:

* self-service регистрация клиента (создание tenant, первый admin, стартовые шаблоны) — 1–2 недели;
* биллинг + подписки + триал + автоблокировка;
* «план как данные»: `plans` → лимиты в движок (не захардкоженные `max_channels`);
* нагрузочное тестирование (мультиарендный стенд: 30 tenants × 3 канала, проверка, что один
  медленный Asterisk не тормозит всех) — без него в SaaS идти нельзя;
* отказоустойчивость: Postgres + реплика, один Redis-лок на tenant для движка, чтобы инстансов
  приложения было несколько;
* миграция существующих клиентов-инстансов в общую базу (скрипт, который проставляет `tenant_id`).

## 5. Что делать прямо сейчас, не дожидаясь SaaS

1. Зафиксировать для себя: **модель продажи = инстанс на клиента** (ступень 0), а не «подписка в одной базе».
2. Ввести нумерацию клиентов и правило именования: `mcm-<код>`, `ats-out-<код>`, порт `91<nn>`,
   поддомен `<код>.ats.example.ru` — дальше всё упирается только в эти имена.
3. Пароль админа выдавать через `--set-password` и требовать смену при первом входе
   (`initial_credentials.txt` в репозиторий не коммитить — см. `docs/SECURITY_CLEANUP.md`).
4. Публичный доступ — только через nginx+TLS; `ATS_HOST=127.0.0.1` оставить как есть.
5. Раз в квартал прогонять `deploy/check.sh` + тесты (`python3 -m unittest discover -s tests`).

## 6. Как перепроверить этот аудит

```bash
cd /opt/ats/app     # или в рабочем клоне
grep -c "CREATE TABLE IF NOT EXISTS" app/db.py
grep -inE "tenant|org_id|workspace" app/db.py | wc -l        # 0 — ключа аренды нет
grep -n "CHECK (id = 1)" app/db.py                             # одна строка настроек
sed -n '8,9p' app/security.py                                  # сессии в памяти
grep -n "max_channels" app/config.py app/engine.py | head
grep -n "if sess\[\"role\"\] != \"admin\"" app/api.py | wc -l   # число ролевых проверок
python3 -m unittest discover -s tests 2>&1 | tail -2           # 356 OK — что ломать не будем
```

Связанные документы: `docs/SECURITY_CLEANUP.md` (что вычищать после настройки),
`docs/MULTICOM_SIP_CONNECT.md` (подключение оператора), `docs/DEPLOY.md` (установка/обновление).
