# ADR-0001: топология для нескольких клиентов — изолированный инстанс на клиента

- Статус: принято (по умолчанию) для ближайшего горизонта; пересмотр при
  >30–50 активных клиентах
- Дата: 2026-10-21
- Контекст: аудит 2026-10-21 (docs/engineering/BASELINE.md §4, ROADMAP),
  вопрос «тысячи клиентов в SaaS»

## Контекст

ATS v2 — single-tenant: одна строка `settings`, нет `tenant_id` ни в одной
из 21 бизнес-таблицы, глобально уникальные логины, один провайдер телефонии
и один Asterisk-контекст на инстанс (см. docs/MULTITENANT_READINESS.md).
Требование «несколько тысяч клиентов» может означать два принципиально
разных продукта, и смешивать их нельзя:

1. **Изолированные инстансы** — каждый клиент в своей БД/настройках/секретах.
2. **Shared multi-tenant SaaS** — общий API, PostgreSQL с tenant_id в каждой
   строке, общие пулы воркеров.

## Рассмотренные варианты

### Вариант 1: изолированный инстанс на клиента (выбран по умолчанию)

Каждый клиент: свой процесс ATS, своя SQLite (или свой schema в PostgreSQL),
свои секреты, свой Asterisk context/endpoint/транк, свой домен за общим
reverse-proxy с TLS. Provisioning — скриптами/контейнерами.

**Плюсы**
- Изоляция данных по построению: забытым `WHERE tenant_id=` невозможно
  утечь данные соседа — класс ошибок №1 shared-модели исключён структурно.
- Текущий код пригоден почти без изменений (после этапов B–C аудита);
  time-to-market — недели, а не месяцы.
- Разные клиенты могут жить на разных версиях/каналах телефонии; падение
  одного инстанса не роняет остальных.
- Аудит/бэкап/удаление данных одного клиента тривиальны (GDPR-стиль
  «удалите всё про нас» = удалить БД).

**Минусы**
- Стоимость хостинга растёт линейно по клиентам; сотни инстансов — сотни
  процессов и БД (SQLite в ~50–150 МБ RAM на инстанс — до нескольких тысяч
  на одном сервере, но обновления/мониторинг — по каждому).
- Обновления: раскатка на N инстансов (нужен deploy-конвейер, он уже есть —
  `deploy/update.sh`).
- Общая аналитика/биллинг — только внешней агрегацией, внутри одного
  инстанса её нет.

### Вариант 2: shared multi-tenant SaaS

Общий кластер API-реплик, PostgreSQL с `tenant_id` во всех таблицах, общие
dialer/CRM-воркеры, Redis для сессий/лимитов, tenant-aware планировщик.

**Плюсы**
- Лучшая утилизация ресурсов, единое обновление, единый биллинг/квоты,
  общие метрики; экономичнее при десятках-сотнях активных клиентов.

**Минусы**
- Требует полного цикла: PostgreSQL+миграции, tenants+RBAC, tenant-контекст
  в каждом запросе и каждом SQL, изоляция настроек/секретов/телефонии,
  распределённый планировщик с lease/idempotency, object storage записей,
  negative-тесты изоляции на каждый маршрут. Это месяцы работы и отдельный
  цикл load-тестов — при текущем состоянии репозитория (аудит §4) делать
  это «на SQLite и одном процессе» нельзя.
- Цена одной ошибки изоляции — утечка данных между клиентами.

## Решение

**По умолчанию — Вариант 1 (изолированный инстанс на клиента).** Основания:
класс ошибок межtenant-утечек исключается архитектурно; текущий код уже
доработан до безопасного single-tenant (этапы B–C аудита); реалистичный
time-to-market; мобильных требований, обязывающих shared, нет.

**Migration path к Варианту 2** (запускается при >30–50 активных клиентах
или явном требовании самообслуживания/биллинга):

1. Сначала — общая инфраструктура вне приложения: reverse-proxy c
   wildcard-TLS, конвейер provision/deprovision инстансов, центральные
   логи/метрики/бэкапы (даже для Варианта 1 это нужно).
2. Перевод инстансов на PostgreSQL (по своей БД/schema на клиента) —
   код перестаёт быть привязан к SQLite, миграции становятся
   версионированными; это же — фундамент для шага 3.
3. Постепенная консолидация: общие таблицы `tenants`/`users` + per-tenant
   schemas в одной БД (middle-ground: изоляция на уровне schema, единый
   биллинг), затем — при необходимости — полная shared-модель по плану
   ROADMAP «Фаза 3» с tenant_id и negative-тестами изоляции.

Отдельно фиксируем: **массовое включение `tenant_id` в текущую SQLite-схему
без scoped-репозитория, RBAC и negative-тестов не делается** — это создаст
иллюзию multi-tenancy при сохранении всех рисков (аудит §3, P1).

## Последствия

- Дорожная карта фазы 2 (нагрузочные/live-тесты) относится к Варианту 1.
- Число «тысячи клиентов» в Варианте 1 упирается в ops-автоматизацию
  (provision/monitoring/updates), а не в код приложения — это фиксируется
  как критерий пересмотра решения.
- Пересмотр ADR: при превышении порога клиентов или при появлении
  требования общего биллинга/самообслуживания.
