# Полный анализ проекта «ATS Dispatcher» (обзвон по 6 линиям)

> Дата анализа: 2026-09-05
> Проанализирован код единственного содержательного коммита `2fd96ec` («Первый коммит: загрузка проекта ATS») — рабочее дерево репозитория.
> Объём: 2 Python-модуля (`server.py` 516 строк, `xp_bridge/xp_bridge.py` 159 строк), однофайловый веб-интерфейс (`static/index.html`, ~94 строки с минифицированным CSS/JS), JSON-«база» в `data/`, служебные BAT/ISS-скрипты сборки.

---

## 1. Резюме (коротко)

Проект — это **локальная (LAN) автоматическая телефонная станция-«обзвонщик»** (robocall dispatcher) на Python + браузерном интерфейсе. Он позволяет:

- вести базу контактов с отметкой «есть разрешение на автодозвон» (согласие на обработку/обзвон);
- редактировать текстовые шаблоны речевых сообщений с подстановками `{name}`, `{phone}`, `{group}`, `{note}`;
- ставить контакты в очередь, а фоновый цикл диспетчера автоматически распределяет их по **6 телефонным линиям**;
- «звонить» либо в **тестовом режиме** (без реальных звонков, для проверки), либо через **COM-порт GSM-модема** с AT-командами;
- озвучивать текст через **Windows SAPI** (или внешнюю команду) и писать в линию, показывая результат вызова в реальном времени;
- вести журнал звонков, импорт/экспорт CSV, собирать EXE через PyInstaller и установщик через Inno Setup.

Ключевая особенность архитектуры: **сервер-диспетчер и «мост» (bridge), управляющий модемами, — это два независимых процесса**, которые общаются не по сети, а **файлами в общей папке `shared/`** (команды → статусы). Это позволяет запускать мост на отдельной машине (например, на старой Windows XP рядом с GSM-модемами), что и объясняет название «XP bridge».

Проект — **рабочий прототип/MVP**, а не законченный боевой продукт: значительная часть кода и данных (входящие звонки, IVR-сценарии, справочник подразделений, запрещённые слова) присутствует в виде заготовок, но не подключена; ряд настроек хранится, но не выполняется; есть проблемы безопасности, надёжности и реальной подачи звука в телефонную линию. Что именно дорабатывать — зависит от цели (см. разделы 7–9).

## 3. Архитектура

```
┌─────────────────────────── Машина «сервер» ───────────────────────────┐
│                                                                        │
│  Браузер оператора ──HTTP/JSON──▶ server.py (веб-сервер, порт 9123)   │
│      (static/index.html)        │  ▲                                  │
│                                 ▼  │ /api/state каждые 2,5 с          │
│        файлы data/*.json  ◀───┤  │   (чтение/запись, RLock)           │
│                                 │                                      │
│        dispatch_loop (фоновый поток, раз в 1 с):                       │
│        очередь → свободная линия → файл-команда в shared/commands/    │
│        чтение статусов из shared/status/ → обновление очереди/журнала  │
└───────────────┬────────────────────────────────────────────────────────┘
                │  общая папка shared/  (локально или сетевой диск/UNC)
┌───────────────▼─────────────────── Машина «мост» (возможно Win XP) ────┐
│  xp_bridge.py (цикл раз в 0,2 с):                                      │
│  shared/commands/*.json ──► AT-набор через pyserial ──► GSM-модем     │
│        │   озвучка: Windows SAPI (powershell) или audio_command        │
│        ▼                                                                │
│  shared/status/*.json  (ringing → connected → done/busy/no_answer/…)   │
└─────────────────────────────────────────────────────────────────────────┘
```

**Ключевые решения архитектуры:**

1. **Два процесса, ноль сетевых API между ними.** Обмен — JSON-файлами: сервер **пишет** в `shared/commands/`, мост **забирает** их в `shared/processed/`; мост **пишет** статусы в `shared/status/`, сервер забирает их в `shared/processed/` (свою). Сломанные файлы — в `shared/bad/`. Это даёт: устойчивость к падению любого процесса (файлы переживают), возможность запускать мост на слабой/старой машине (XP) рядом с COM-портами, простую отладку «в файлах».
2. **Хранение данных — простые JSON-файлы** в `data/` с атомарной записью через `.tmp` + `replace()` и общей блокировкой `threading.RLock`. Достаточно для тысяч контактов, но не для «боевой» многопользовательской базы.
3. **Веб-интерфейс — один HTML-файл**, опрашивает `/api/state` раз в 2,5 секунды (polling). Никаких фреймворков, работает из коробки.
4. **Безопасность — простая сессия по токену** (`X-Admin-Token`, 8 ч), пароль с солью (SHA-256), хранится в `data/settings.json`. Но чтение данных не защищено (см. 8.1).
5. **Тестовый режим** (`test_mode: true` по умолчанию) — мост не звонит, а проигрывает сценарий ringing→connected→done со сном; удобно для демонстрации.

## 4. Как работает проект (пошагово)

### 4.1. Запуск
1. `run_web_ats.bat` → `server.py`.
   - `init_data()` создаёт `data/*.json` с умолчаниями, если их нет; при первом запуске генерирует соль и хэш пароля `admin1234`.
   - Поднимается `ThreadingTCPServer` на `0.0.0.0:9123` (если порт занят — перебор запасных 9123→8090→8091→8080→5050; также можно переопределить порт переменной окружения `ATS_PORT`).
   - Запускается фоновый поток `dispatch_loop`.
   - Автоматически открывается браузер на `http://127.0.0.1:9123`.
2. `start_xp_bridge.bat` → `xp_bridge.py` (можно на той же или другой машине, если `shared/` расшарена).
3. В браузере вход: логин `admin`, пароль `admin1234`.

### 4.2. Работа оператора в интерфейсе
- **Обзор (dashboard)**: 6 карточек линий (статус: `offline/ready/dialing/ringing/connected/done/failed/error/no_answer/busy`, режим, COM-порт, текущий вызов, последняя ошибка); метрики: контактов, в очереди, активных вызовов, завершено; кнопка «Добавить разрешённые контакты» — поставить всю базу с согласием в очередь.
- **База обзвона**: таблица контактов (имя, телефон, группа, согласие, примечание), добавление/редактирование в модальном окне, выбор чекбоксами, «В очередь», импорт CSV текстом, экспорт CSV (кнопка-ссылка), удаление.
- **Шаблоны озвучки**: тексты с подстановками `{name} {phone} {group} {note}`, признак «активен», предпрослушивание через `speechSynthesis` браузера (ru-RU).
- **Очередь**: таблица созданных звонков со статусами; очистка ожидающих.
- **6 линий**: на каждую линию — режим (`test`/`com`), COM-порт, скорость, AT-префикс набора (`ATD`), суффикс (`;`), команда отбоя (`ATH`), «линия включена», внешняя команда подачи аудио (`audio_command`).
- **Журнал**: последние до 1000 записей звонков: время, имя, телефон, линия (id), статус, результат.
- **Настройки**: параллельных линий (1–6), окно обзвона (часы), пауза линии, требовать согласие, тестовый режим, смена логина/пароля.

### 4.3. Цикл автоматического обзвона (сервер, `dispatch_loop`, раз в 1 с)
1. `scan_status()` — собирает новые файлы из `shared/status/` и обновляет: статус линии, статус элемента очереди, запись журнала (`result`, `finished_at`); файл перемещается в `shared/processed/` (битые — в `shared/bad/`).
2. Если сейчас **вне разрешённого окна времени** (`allowed_hours_start..end`) — сон и повтор.
3. Выбираются **активные линии**: `enabled` и статус `ready` или `offline`; количество ограничено `max_parallel` (но не более 6).
4. Берётся первый элемент очереди со статусом `queued`.
5. Проверки: контакт и шаблон существуют (иначе — `error`); если `consent_required` и у контакта нет `consent` — `blocked_no_consent`.
6. Формируется текст сообщения: `render_text()` подставляет поля контакта в шаблон.
7. `write_command()` создаёт файл `shared/commands/call_{id}_{cmd}.json` с полной командой (включая **копию параметров линии**).
8. Элемент очереди: `dialing`, фиксируются `started_at`, `line_id`, `command_id`; линия: `dialing` + `current_call_id`; в журнал добавляется запись.
9. Повтор, пока есть свободные линии и ожидающие элементы. Очередь и линии сохраняются на диск.

### 4.4. Мост (bridge) — исполнение звонка
`xp_bridge.py` опрашивает `shared/commands/` каждые 0,2 с. Для каждого нового файла (защита от дублей в рамках процесса через `ACTIVE`) в отдельном потоке `handle()`:

- режим **`test`** → `call_test()`: последовательно пишет статусы `ringing` → `connected` → `done` с паузами (эмуляция);
- режим **`com`** → `call_com()`:
  1. открывает `serial.Serial(port, baud, timeout=1)`;
  2. отправляет `ATD<номер>;\r` (голосовой вызов);
  3. читает ответы модема до 35 с, ожидая `CONNECT`/`VOICE CALL: BEGIN`/`OK`; на `BUSY` → статус `busy`, на `NO CARRIER`/`NO ANSWER` → `no_answer` (пишет отбой `ATH`);
  4. при соединении → `connected`, запускает озвучку: `speak()` — либо внешняя команда из `audio_command` (в `{text}` подставляется текст), либо **PowerShell + SAPI** (`SAPI.SpVoice`);
  5. ждёт окончания озвучки (до 120 с), отбой `ATH`, статус `done`.
- Файл команды перемещается в `shared/processed/` (или `shared/bad/` при ошибке).
- Все события логируются в `shared/log/xp_bridge.log`.

### 4.5. Жизненный цикл статусов звонка
```
queued → dialing → (мост:) ringing → connected → done
                              ↘ busy / no_answer / failed / error
контакт без согласия → blocked_no_consent
нет контакта/шаблона → error
```
Сервер узнаёт финальные статусы из файлов `shared/status/` и закрывает звонок в журнале (`finished_at`). Начальные статусы `dialing`/`ringing`/`connected` висят в очереди и журнале, пока мост не пришлёт финал.

### 4.6. HTTP API (сервер)
| Метод и путь | Назначение | Авторизация |
|---|---|---|
| `POST /api/auth/login` | Логин, выдаёт токен (8 ч) | нет |
| `POST /api/auth/logout` | Сброс токена | токен |
| `GET /api/state` | Всё состояние: контакты, шаблоны, линии, очередь, журнал, настройки (без пароля), `admin`, `lan_ip` | **нет** (см. 8.1) |
| `GET /api/export/contacts.csv` | Экспорт CSV (BOM, разделитель `;`) | нет |
| `POST /api/contacts/save` `…/delete` `…/import` | CRUD контактов, импорт (нормализация телефона: только цифры и первый `+`; без дублей по номеру) | токен |
| `POST /api/templates/save` `…/delete` | CRUD шаблонов | токен |
| `POST /api/lines/save` | Сохранить параметры линии (merge со старой) | токен |
| `POST /api/lines/reset` | Все линии → `offline`, сброс текущих вызовов | токен |
| `POST /api/queue/add` | Постановка контактов в очередь (макс. 20 000 записей) | токен |
| `POST /api/queue/clear` | Удалить ожидающие (`queued`) | токен |
| `POST /api/settings/save` | Сохранить настройки; смена логина/пароля | токен |

Любая мутация требует заголовка `X-Admin-Token`. При 401 фронтенд сам «разлогинивается».

## 5. Модель данных (ключевые поля)

- **Контакт**: `id, name, phone (нормализованный), group, note, consent (bool)`.
- **Шаблон**: `id, name, text (с {name}{phone}{group}{note}), active`.
- **Линия** (их 6 по умолчанию): `id, name, enabled, mode (test|com), com_port, baudrate, dial_prefix(ATD), dial_suffix(;), hangup_command(ATH), audio_command(«»), status, current_call_id, last_error, last_seen`.
- **Элемент очереди**: `id (uuid hex), contact_id, template_id, status (queued|dialing|…|done|error|no_answer|busy|failed|blocked_no_consent), created_at, started_at, completed_at, line_id, command_id`.
- **Запись журнала**: `id, datetime, contact_id, name, phone, line_id, template_id, text (готовое сообщение), status, result, finished_at`.
- **Команда мосту** (файл): `id, kind=outbound_call, created_at, call_id, line_id, phone, text, contact_name, template_id, line{…полная копия линии…}`.
- **Статус моста** (файл): `id, datetime, command_id, call_id, line_id, status, status_text`.
- **Настройки**: логин/соль/хэш пароля, host, port, `max_parallel`, `retry_count`, `retry_delay_sec`, `line_cooldown_sec`, окно времени `allowed_hours_start/end`, `consent_required`, `test_mode`.

## 6. Формат обмена и сборки

- **CSV базы**: `Имя;Телефон;Группа;Примечание;1` — последняя колонка = согласие (1/да/yes/true/+).
- **Сборка EXE** (`build_exe_win10.bat`): `pip install -r requirements.txt`; PyInstaller `--onefile`:
  - `ATS_Dispatcher` = `server.py` + `--add-data "static;static"`;
  - `ATS_6Line_Bridge` = `xp_bridge/xp_bridge.py` + `--hidden-import serial`.
  - В «замороженном» виде пути считаются от папки EXE (данные — рядом в `data/`, `shared/`).
- **Установщик** (`build_setup.bat` + `build_setup.iss`, Inno Setup) упаковывает EXE + `data/`, `static/`, `xp_bridge/`, `shared/`, README, создаёт ярлыки. **Сейчас не работает из-за рассинхрона имён** (см. 8.8).

## 7. Что реализовано лишь частично / мёртвый код

1. **Входящие звонки — только заготовка.** Есть `xp_bridge/test_incoming_call.py`, который кладёт файл «входящего звонка» в `shared/inbox/`, но: папка `inbox` **никем не читается**, мост не детектирует `RING`/CLIP на COM-порту, сервер не имеет ни API, ни UI для входящих. Вместе с этим лежат готовые, но неиспользуемые данные:
   - `data/departments.json` — справочник подразделений с телефонами, графиком, ключевыми словами (дежурный оператор 2240, бюро пропусков 2245, справочная 2238);
   - `data/scripts.json` — сценарий автоответчика/IVR (приветствие «разговор записывается», меню «нажмите 1/2/3», «соединяю с дежурным», предупреждение о риске и т.д.);
   - `data/forbidden.json` — «опасные» слова (угроза, экстренно, нарушение…) с уровнем риска и действием;
   - `data/actions.json`, `data/calls.json` — пустые журналы действий/звонков;
   - `records/` — папка «под запись разговоров», не используется;
   - `imports/`, `exports/` — не используются (экспорт идёт прямо из браузера через API).
   Это выглядит как **второй задуманный сценарий — «диспетчер/секретарь» с автоответчиком и маршрутизацией** (оператор «бюро пропусков» и т.п.), который не доведён и не подключён к коду.
2. **`xp_bridge_config.json` не читается** мостом: путь обмена и параметры зашиты в код (`ROOT = ../shared`). Значит, конфигурация «мост на отдельной машине через сетевой диск» не настраивается, несмотря на заявленную в файле опцию `exchange_path`.
3. **Настройки, которые хранятся, но не работают:**
   - `retry_count`, `retry_delay_sec` — повторов нет вообще: `busy`/`no_answer`/`failed` навсегда завершают элемент очереди;
   - `line_cooldown_sec` — пауза линии после звонка не соблюдается (линия снова `ready` сразу после обработки статуса);
   - `host`/`port` в настройках меняются только через перезапуск сервера, мгновенного применения нет;
   - `test_mode` принудительно «прошивается» в строку `line["mode"]="test"` **в диспетчере** — это работает, но нелогично: режим теста должен решаться в мосте, а не перезаписывать настройку линии.
4. **`template.active` не проверяется при диспетчеризации** — в очередь можно поставить и «неактивный» шаблон (фронтенд прячет его из выпадающих списков, но API это не защищает).
5. **Заготовки статусов, которых нет в UI-стилях/счётчиках**: `busy`, `no_answer`, `failed`, `error`, `blocked_no_consent` приходят в очередь и журнал, но метрики считают только `done`, а «активные» — по списку `dialing/ringing/connected`. Итог дня удобно не подводится.
6. **Журнал не растёт бесконечно** (обрезается до 10 000 записей), но «хвост» не выгружается в файл — история теряется при переполнении (обрезка `logs[-10000:]`).

## 8. Ошибки и слабые места

### 8.1. Безопасность (важно)
1. **`GET /api/state` и `GET /api/export/contacts.csv` не требуют авторизации.** Любой в локальной сети (а сервер слушает `0.0.0.0`) получает полную базу ФИО+телефонов (персональные данные) и может выгрузить CSV. При включённом «боевом» режиме это ещё и фактический инструмент несанкционированного обзвона чужими руками.
2. **Пароль по умолчанию `admin1234`** известен; интерфейс даже подставляет его в поле пароля. Если не сменить — тривиальный вход. Нет блокировки перебора, нет ролей («оператор» = «админ»).
3. **HTTP без шифрования** — трафик (в т.ч. пароль и токен) идёт открыто. Для локальной сети терпимо, для доступа через интернет/удалёнку — нет.
4. **Токен живёт 8 часов** и хранится в `localStorage` (XSS-уязвим, хотя контент в основном экранируется через `esc()` — это плюс).
5. `run_web_ats_safe.bat` **не делает сервер безопаснее**: он задаёт `ATS_HOST` и аргументы `--host/--port`, но `server.py` их **не читает** (нет `argparse`; `ATS_HOST` не используется вовсе, только `ATS_PORT`). Сервер всё равно поднимется на `0.0.0.0` из настроек.
6. Ошибки в `dispatch_loop` глушатся голым `except Exception: pass` — сбой незаметен (см. 8.4).
7. CSV-экспорт и ответы JSON отдают данные без авторизации (см. п.1); в HTML интерфейс по умолчанию вшит известный пароль в атрибут `value` — привет любому, кто откроет страницу.

### 8.2. Надёжность цикла звонков (важно для боевого режима)
1. **Нет watchdog'а на «зависшие» вызовы.** Если мост упал/не забрал команду/завис на озвучке, элемент очереди и линия навсегда останутся в `dialing/ringing/connected` (в т.ч. после перезапуска моста: сервер не знает, что команда «пропала»). Нужны: heartbeat моста, таймауты по `started_at`, автосброс линий и возврат элементов в `queued`.
2. **`last_seen` линии обновляется только когда пришёл статус** — то есть фактически это не heartbeat, а «последняя активность». Отличить «модем молчит» от «мост умер» нельзя.
3. **Нет повторов** занято/нет-ответа (см. 7.3), хотя настройки для этого есть.
4. **Состояние линий при старте**: линия, оставшаяся в `dialing` после падения сервера, больше не будет выбрана диспетчером (активны только `ready|offline`) — реально «висеть» будет и после рестарта, пока не нажать «Сбросить линии» вручную.
5. **Окно времени** сравнивается как строка `"ЧЧ:ММ"` — корректно, но не поддерживает: интервал через полночь, выходные/праздники, несколько окон, часовой пояс настраивается только системным временем.
6. `max_parallel` ограничен сверху 6 — «настройка» вводит в заблуждение при большем числе линий.

### 8.3. Телефония и звук (самый большой «боевой» риск)
1. **Реальная передача звука в линию не гарантируется.** В коде озвучка = PowerShell/SAPI, говорящий в **системный аудиовыход** Windows (или `audio_command`, запускающий внешний процесс). Чтобы абонент услышал голос, звук должен попасть в аудиотракт модема/АТС (разъём гарнитуры модема ↔ звуковая карта, USB-аудиоустройство, голосовой режим модема с передачей PCM по COM вроде `AT#VBS`/`AT+CSDVC`/Quectel voice-команд и т.п.). Это зависит от конкретного железа; в README это честно отмечено, но из «коробки» звонок = соединение без звука для многих моделей модемов.
2. **Детекция соединения упрощена**: ждёт `CONNECT`/`VOICE CALL: BEGIN`/`OK`; не обрабатывает `NO DIALTONE`, `ERROR`, `+CME ERROR`, «занято» по тону, слепые тайминги; `OK` сразу после `ATD;` может приходить до реального соединения (для голосовых вызовов типичен `ATD` без `;` для передачи тона и ожидания `CONNECT` только в data/voice-режиме).
3. **Один COM-порт = одна линия** и всё последовательно: пока идёт озвучка (до 120 с) или ожидание, линия занята — это ок для 6 модемов, но нет очереди на линии с учётом «линия освободится через N сек».
4. Если `pyserial` не установлен на машине моста — статус `error`, но без переустановки повтор будет вечным.

### 8.4. Мост: гонки и отказоустойчивость
1. **Нет межпроцессного захвата файла-команды.** Защита `ACTIVE` работает только в пределах одного процесса. Если на одну папку `shared` смотрят два моста (или мост перезапущен и «догоняет» старые файлы параллельно с новым), **один и тот же звонок может быть набран дважды**. Нужен атомарный захват (переименование с `O_EXCL`, блокировка файла) до старта звонка.
2. Падение моста **посреди** звонка (после набора) не пишет статус → сервер не узнает результат (см. 8.2.1); повторный запуск снова возьмёт ту же команду (это и плюс «не потеряли», и минус «можем позвонить повторно, не зная, что уже дозвонились»).
3. `call_com()` выполняется в потоке на команду — при «залипании» COM-порта поток висит; таймаут только на чтение ответа 35 с, на `serial.Serial()` открытие/озвучку/закрытие — жёстких таймаутов нет.
4. Нет лимита на число потоков моста: 100 команд в папке = 100 потоков и 100 COM-портов (на практике не встретится, но дешевле было бы обрабатывать последовательно, т.к. звонок и так занимает порт).

### 8.5. Фронтенд и UX
1. `setInterval(load, 2500)` грузит **всё** состояние каждые 2,5 с (журнал до 1000 строк, очередь до 500) — при росте базы станет тяжело; нет инкрементальных обновлений, сортировок/фильтров/поиска (журнал без фильтров непрактичен), нет пагинации по-настоящему (только срез последних).
2. Нет подтверждения смены пароля/проверки текущего пароля; нет «сменить пароль при первом входе».
3. Нет кнопки «снять с линии/прервать звонок» (kill-команда мосту не предусмотрена протоколом).
4. Предпрослушивание шаблона браузером — синтез на машине оператора, честно помечен как предпросмотр.
5. Значения «часы обзвона» не проверяются (можно `start > end` — обзвон не пойдёт весь день без внятной ошибки).
6. `alert()` для сообщений — некрасиво, но работает; мелкие недочёты вёрстки (`grid6` жёстко 6 колонок при `max_parallel < 6` и т.п.).

### 8.6. Логирование и наблюдаемость
- Сервер пишет только в JSON-файлы и консоль; систематического файла-лога сервера нет; исключения `dispatch_loop` проглатываются (`except Exception: pass`) — **обнаружить сбой можно только визуально**.
- Мост пишет `xp_bridge.log`, но без ротации.
- Нет метрик/счётчиков результативности за день (сколько done/busy/no_answer, % успешных), нет экспорта журнала.

### 8.7. Запуск и конфигурация
- `run_web_ats_safe.bat` бессмысленен в части «safe» (см. 8.1.5): `ATS_HOST` и CLI-аргументы игнорируются.
- Порт выбирается «первый свободный из списка» — при конфликте оператор может не заметить, что открылся не 9123, а 8090 (в консоли печатается, но интерфейс с «зашитым» адресом не перезагружается... фактически `webbrowser.open` открывает правильный).
- Нет service-установки (автозапуск как служба/в автозагрузке) — для «дежурного» сценария это критично.

### 8.8. Сборка и установщик
- **Рассинхрон имён EXE**: `build_exe_win10.bat` создаёт `ATS_Dispatcher.exe` и `ATS_6Line_Bridge.exe`, а `build_setup.iss` и `build_setup.bat` ожидают `ATS_Web_Dispatcher.exe` → установщик не соберётся, пока не поправить имя (в `.iss` задан `MyAppExeName`).
- `build_setup.iss` не включает в установщик **мост** как отдельно запускаемый EXE (в `xp_bridge\*` попадёт исходник, а не собранный `ATS_6Line_Bridge.exe`), и нет ярлыка/запуска моста после установки.
- PyInstaller `--onefile` для моста, который должен работать 24/7 на XP, — медленный старт и распаковка во временную папку; для XP современный PyInstaller/Python вообще не собирает (нужен отдельный стек, если XP реально нужен).
- `build_xp_bridge_exe.bat` дублирует сборку моста из `build_exe_win10.bat` с другим именем (`ATS_XP_Bridge`) — путаница в артефактах.
- `AppId` в `.iss` содержит «ATS-DISPATCHER» внутри GUID — формально допустимо, но не по канону.

### 8.9. Масштабируемость и данные
- JSON-файлы + полное перечитывание при каждом цикле и каждом HTTP-запросе: при десятках тысяч контактов и большой истории начнёт тормозить; нет транзакций между файлами (очередь ↔ журнал ↔ линии пишутся раздельно — при сбое между записями возможна рассинхронизация).
- Очередь обрезается до 20 000, журнал — до 10 000 «молча» (потеря истории без уведомления).
- Число линий зашито: `DEFAULT_LINES` (6), `active[:max(1,min(6,...))]`, сетка «6 линий», `min=1 max=6` в UI.

## 9. Какие изменения потребуются

Точный список зависит от цели. Ниже — приоритизированные пакеты.

### Сценарий A: «Хочу довести до рабочего исходящего обзвона» (основной)

**P0 — критично (безопасность и закон):**
1. Закрыть `/api/state` и `/api/export/contacts.csv` авторизацией (или ввести токен «только чтение» для оператора без прав записи). Разделить роли: оператор (просмотр, постановка в очередь) и администратор.
2. Сменить пароль по умолчанию (генерировать случайный при первом запуске и печатать в консоль; принудительная смена при первом входе), блокировка после N неудачных попыток.
3. Исправить `run_web_ats_safe.bat`: сервер должен реально читать `ATS_HOST`/`--host`/`--port`; либо по умолчанию слушать `127.0.0.1`, а наружу открывать явно.
4. (Если доступ нужен не только по LAN) — HTTPS через reverse-proxy или встроенный TLS.

**P0 — корректность звонков:**
5. Watchdog и heartbeat:
   - мост периодически пишет «я жив» (например, `shared/status/_heartbeat.json` или обновляет `last_seen`);
   - сервер: если линия/вызов в `dialing/ringing/connected` дольше N минут — статус `error/timeout`, линию в `ready`, элемент обратно в `queued` (с учётом попыток) или в `failed`;
   - при старте сервера «зависшие» (`dialing/…`) элементы и линии приводить к согласованному состоянию.
6. Реализовать `retry_count`, `retry_delay_sec`, `line_cooldown_sec` (поля уже есть): занято/нет ответа → повтор через интервал до N раз; после звонка линия отдыхает `line_cooldown_sec`.
7. Разобраться со звуком под конкретное железо (см. 8.3.1): задокументировать поддерживаемые модемы, добавить в `audio_command` возможность передавать готовый WAV/MP3 (генерировать файл из текста заранее и проигрывать в устройство линии), либо перейти на проверенную схему «GSM-шлюз/SIP-транк + Asterisk/Freeswitch» — тогда вся логика озвучки становится тривиальной (воспроизведение файла в канал).
8. Проверить юридическую сторону: автообзвон регламентируется (152-ФЗ «О персональных данных», 38-ФЗ «О рекламе» для рекламных обзвонов) — consent в проекте есть, но нужен порядок фиксации согласия и отказа (отказ = чёрный список). Отдельно: не звонить повторно тем, кто уже ответил/отказался.

**P1 — эксплуатация:**
9. Файловый лог сервера + лог моста с ротацией; убрать голые `except Exception: pass` в `dispatch_loop` (логировать и продолжать).
10. Сводка за день в UI: done/busy/no_answer/error, % успешных; фильтры и поиск по журналу; экспорт журнала в CSV.
11. Автозапуск как служба Windows (или запись в автозагрузку) + автостарт моста.
12. Резервное копирование `data/` (архив по расписанию), очистка старых `shared/processed|bad|status`.
13. Настройки окна времени: интервал через полночь, дни недели; валидация полей.
14. Кнопка «Прервать вызов» (kill-команда мосту через `shared/commands`).

**P2 — развитие:**
15. SQLite вместо JSON (или, минимум, нормальное хранение истории), пагинация/инкрементальная загрузка в UI.
16. Настраиваемое число линий (снять «магию 6»).
17. Очередь: пауза/приоритеты/снятие отдельных элементов, «не дозваниваться повторно в течение N дней», автоматическое исключение номеров из чёрного списка.
18. Импорт CSV файлом (drag&drop), выбор стратегии при дублях (пропустить/обновить).
19. Проверка `template.active` на сервере при постановке в очередь.

### Сценарий B: «Нужен приём входящих / диспетчер-автоответчик»
В репозитории уже есть «половина» этого сценария (см. раздел 7.1), но не хватает главного:
1. **Детектор входящего звонка** в мосте: мониторинг COM-порта на `RING` + CLIP (`+CLIP`) либо сигнал с АТС; сейчас мост умеет только исходящие.
2. **Обработчик входящих на сервере**: приём файлов из `shared/inbox`, создание записи в `calls.json`, запуск IVR-сценария из `scripts.json`.
3. **IVR-движок**: воспроизведение приветствия/меню, приём DTMF (нажатия 1/2/3) — через AT-команды модема (`AT+VTS`/`+DTMF`) или распознавание речи (отдельная система), маршрутизация по `departments.json` (ключевые слова → подразделение), реакция на `forbidden.json`.
4. **Запись разговоров** в `records/`, журнал действий в `actions.json`, «перевод на дежурного/подразделение» через трансфер (внутренний номер 2240/2245/2238 или второй COM).
5. UI: вкладка «Входящие», карточка звонка, список подразделений, редактор сценариев, редактор «запрещённых» слов.
   Это по сути **отдельный большой этап** — по объёму сравним с текущим проектом или больше.

### Сценарий C: «Чистка и рефакторинг»
1. Удалить (или явно пометить) мёртвые данные/файлы: `actions.json`, `calls.json`, `departments.json`, `forbidden.json`, `scripts.json`, `inbox`-тест, `records/`, `imports/`, `exports/`, неиспользуемый `xp_bridge_config.json` — если сценарий B не планируется.
2. Починить сборку: синхронизировать имена EXE (`build_exe_win10.bat` ↔ `build_setup.iss`), включить мост в установщик, удалить дублирующий `build_xp_bridge_exe.bat`, выровнять `README_RU.txt`.
3. Вынести общие константы (пути, число линий, статусы) и схему данных в одно место; добавить валидацию входящих JSON.
4. Покрыть тестами: диспетчерский цикл (окно времени, согласие, повторы), импорт CSV, протокол моста (можно интеграционно: сервер + мост в `test`-режиме, без модема).
5. Переписать фронтенд аккуратно (сейчас всё в одной минифицированной строке — тяжело поддерживать), вынести JS/CSS в файлы при желании.

### Предлагаемая «дорожная карта» (если цель — боевой исходящий обзвон)
1. **Неделя 1–2 (безопасность + стабильность цикла):** п. A-P0-1…3, A-P0-5, A-P0-6, A-P1-9, A-P1-12.
2. **Неделя 2–4 (звук и железо):** A-P0-7: тест на реальных модемах, схема подачи звука, `audio_command` с WAV; протокол статусов дополнить «начало/конец озвучки».
3. **Неделя 4–6 (эксплуатация):** A-P1-10…14, служба Windows, бэкапы.
4. **Далее (по мере необходимости):** A-P2, или сценарий B, или рефакторинг.

## 10. Открытые вопросы к владельцу проекта

Чтобы дать точный план изменений, нужно уточнить:

1. **Цель эксплуатации**: реальный автообзвон абонентов (маркетинг/напоминания/информирование) или внутренняя АТС-диспетчерская с приёмом входящих? От этого зависит 80% плана (сценарий A vs B).
2. **Оборудование**: какие именно модемы/АТС/линии (модели GSM-модемов, USB-голосовые, FXO-шлюзы, SIP-транк)? Сейчас заявлен «стандартный голосовой GSM-модем», но звук в тракт не гарантирован.
3. **Масштаб**: сколько контактов, звонков в день, одновременно работающих операторов?
4. **Машины**: сервер и мост на одном ПК или разных (XP-машина рядом с линиями — реальна ли?); нужен ли доступ из интернета?
5. **Юриспруденция**: база с согласиями — своя (клиенты дали согласие) или чужая? Нужен ли учёт отказов (чёрный список)?
6. Нужен ли **приём входящих** (сценарий «бюро пропусков/дежурный») — судя по `departments/scripts/forbidden`, задумывался.

## 11. Итоговая оценка

| Критерий | Оценка |
|---|---|
| Замысел и архитектура | Хорошие: два процесса с файловым обменом — просто, отказоустойчиво, отлаживаемо |
