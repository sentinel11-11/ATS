# LIVE-тест МегаФон ВАТС: один номер, один сотрудник, один клиент

Цель: подтвердить на живой ВАТС то, что mock проверить не может.
Не подключать остальные номера, пока все 15 шагов не зелёные.

Предусловия: ATS запущен с доступом из интернета по HTTPS
(вебхуки ВАТС идут на `https://<ваш-домен>/api/v2/webhooks/megafon`).

## 0. Подготовка (панель ВАТС → Интеграция с CRM → Ваша CRM / REST API)

1. Создайте интеграцию, запишите **домен** (`https://....megafon.ru`),
   **«Ключ для авторизации в АТС»** (= наш `api_key`, заголовок `X-API-KEY`),
   придумайте **crm_token** (любая случайная строка).
2. Callback URL интеграции: `https://<ваш-домен>/api/v2/webhooks/megafon`.
3. Включите запись разговоров (иначе `link` в history будет пустым).

## 1. Настройка ATS

4. В `settings.megafon_vats` (Настройки → provider_config JSON):
   `base_url` = домен ВАТС, `api_key` или env `ATS_MEGAFON_API_KEY`,
   `crm_token` или env `ATS_MEGAFON_CRM_TOKEN`,
   `default_user` = логин тестового сотрудника, `timeout_sec` = 15.
5. Включите запись звонков в ВАТС (Настройки домена → Запись звонков,
   `GET /record`: `external: true`), иначе записей не будет.

## 2. Проверки чтения (curl с `X-API-KEY`, сверка с панелью)

6. `GET /crmapi/v1/users` — виден тестовый сотрудник (логин!).
7. `GET /crmapi/v1/telnums` — виден тестовый номер, `disabled: false`.
8. `GET /crmapi/v1/caller-ids/telnums` — у тестового номера `enabled: true`.
   Если `false` — исходящие с него ВАТС запретит (ATS такой номер не выберет
   после стадии caller-id pool; сейчас сверяйте вручную).

## 3. Исходящий звонок (ATS → сотрудник → клиент)

9. Добавьте номер в пул ATS (провайдер `megafon_vats`), создайте контакт
   тестового клиента (с согласием!) и кампанию `flow=operator`, запустите.
10. Ожидается: сначала звонит телефон сотрудника (`default_user`), после
    ответа — дозвон клиенту. На телефоне клиента — тестовый номер (clid).
11. В логе ATS НЕ должно быть `ВНИМАНИЕ: запрошен clid=...` (это значит,
    ВАТС подставила свой номер — разбираться с `caller-ids`).
12. Кампания завершается `operator_ok`; карточка звонка показывает запись
    (`recording_url`), длительность, `external_status=Success`.

## 4. Ключевое допущение для сверки (смотреть логи/БД!)

13. Для исходящего callback ВАТС шлёт `ACCEPTED`. Мы трактуем его как
    «клиент на линии». Сверьте по времени: если `ACCEPTED` приходит в момент
    ответа **сотрудника** (клиент ещё не звонился) — сообщите, и мы введём
    двухфазную модель (ACCEPTED=менеджер, разговор=по history/COMPLETED).
    Признак проблемы: `wait_operator` появляется раньше, чем звонит клиент.

## 5. Входящий звонок и contact

14. Позвоните с тестового клиента на тестовый номер. Ожидается: карточка
    входящего в UI (SSE `call` + `incoming`), имя из ATS-контактов на экране
    телефона сотрудника (ответ `contact`), после разговора — `done_ok`,
    запись и `history` без дублей (`provider_events`: 1 событие = 1 строка).
    Пропущенный входящий → задача «Перезвонить клиенту» в CRM.

## 6. Повторы и статусы

15. В панели ВАТС (или повторным POST) продублируйте любой вебхук:
    в логе ATS — `дубль вебхука … — пропущен`, дублей звонков/попыток нет.
    Проверьте `COMPLETED` без `ACCEPTED` (сброс во время гудков) — звонок
    должен уйти в `failed`+ретрай, а не зависнуть.

## Критерии приёмки

- [ ] Шаги 6–8: чтения совпадают с панелью
- [ ] Шаги 9–12: исходящий цикл зелёный, clid верный
- [ ] Шаг 13: семантика ACCEPTED подтверждена (или заведено уточнение)
- [ ] Шаг 14: входящий цикл зелёный, contact отдаёт имя
- [ ] Шаг 15: дубли давятся, gaps финализируются

Только после этого: второй номер, затем — остальные. МТС/билайн — отдельно,
после определения их транспорта (не через этот провайдер).
