## 1. «Перевод» ответа заказчика: что он на самом деле хочет

Исходная речь (машинная расшифровка, сжато):

> «…первая цель — подменные номера для самостоятельного звонка, потому что номер быстро сжигается: сделал сто звонков — уже „Защитник“ срабатывает у абонента. Нужна подменка номеров. Потом карусель звонков, автодозвон, где звонок должен переключаться на сотрудника. Потом — ИИ-агент: дозвон идёт, агент спрашивает основные критерии, как бот. Входящий, наверное, тоже должна принимать, но… сейчас у меня обычная телефония — МегаФон „Ювис“ (UIS), настроена интеграция в CRM: заходишь в сделку, жмёшь „позвонить“ — идёт звонок, сразу работа по сделке. Если всё то же самое делать и запустить карусель исходящих, а потом перезвоны — перезвоны вряд ли будут работать на этих номерах, потому что при обмене/ротации номеров это плохо работает. То есть входящих, по сути, не будет. **Главная задача — исходящие звонки и дозвон.**»

### 1.1. Структурированные требования (R1…R8)

| № | Требование (формулировка заказчика) | Наш перевод в техническое требование | Приоритет |
|---|---|---|---|
| R1 | «Подменные номера / самостоятельный звонок» | Исходящие звонки **от имени компании**, с возможностью выбора номера-источника (Caller ID) из **пула выделенных номеров** | P0 |
| R2 | «Сто звонков — „Защитник“ срабатывает» | Управление **репутацией номеров**: ротация пула, лимиты звонков/номер/день, «остывание» номеров, минимизация жалоб, верификация номера у оператора/антиспам-систем. **Важно: „подмена“ на чужие/произвольные номера в РФ блокируется на уровне операторов (система „Антифрод“, 126-ФЗ) — см. раздел 10. Работаем только со своими номерами.** | P0 |
| R3 | «Карусель звонков» | **Кампании обзвона**: загрузка списков (из CRM/CSV), автоматический прогон по списку, «карусель» = последовательный/циклический обзвон с повторными попытками | P0 |
| R4 | «Автодозвон» | Автоматические повторные попытки (занято/нет ответа/сброс) по правилам: интервал, максимум попыток, окно времени | P0 |
| R5 | «Переключаться должно на сотрудника» | Когда абонент ответил и нужен живой диалог (или это «горячий» лид) — **перевод звонка на свободного сотрудника** (ACD-очередь операторов, горячий трансфер с контекстом) | P0 |
| R6 | «ИИ-агент, спрашивает критерии, как бот» | **Голосовой ИИ-агент**: после ответа абонента ведёт диалог по сценарию, задаёт квалификационные вопросы, фиксирует ответы, решает: завершить / передать сотруднику / создать задачу в CRM | P0 (этап 2–3) |
| R7 | «Входящий должна принимать, но перезвоны на этих номерах не заработают» | Входящие звонки и перезвоны на ротируемые номера — **не основная задача**; поддержать как опцию на выделенном «стабильном» номере, но не в MVP | P1 |
| R8 | «Сейчас МегаФон UIS + интеграция в CRM (клик-ту-колл из сделки)» | Новый функционал должен **интегрироваться с текущей телефонией (UIS) и CRM**: звонок по кнопке из сделки, запись результата обратно в сделку | P0 |

### 1.2. Целевой продуктовый сценарий (как это будет работать)

```
1. Менеджер/робот формирует кампанию: список (CRM/CSV), сценарий, время, пул номеров.
2. Диалер сам дозванивается (карусель + автодозвон), Caller ID меняется по пулу номеров,
   соблюдая лимиты репутации.
3. Абонент ответил →
     а) ИИ-агент (или IVR-бот) задаёт квалификационные вопросы «как бот»;
     б) критерии не пройдены / не интересно  → вежливое завершение, статус в CRM;
     в) критерии пройдены / нужен человек    → «горячий» перевод на свободного сотрудника
        (сотрудник уже видит карточку/сделку абонента);
     г) абонент сразу «живой» и заказчик хочет человека  → перевод на сотрудника без бота.
4. Результат каждого звонка пишется в журнал и в CRM-сделку (статус, запись, теги, оценка).
5. «Сотрудник занят» → звонок встаёт в очередь операторов или формируется задача «перезвонить».
```


### 1.3. Ключевое решение по этапности (владелец проекта, 2026-09-05)

**Сначала тестируем проект на номерах, которые у клиента уже есть** (сейчас это номера в МегаФон «Ювис» / UIS), **затем заключаем договоры с операторами-компаниями (МегаФон, МТС и др.)** и только тогда масштабируемся на выделенных пулах номеров и SIP-транках.

Последствия для плана:
1. Пилот не зависит от переговоров с операторами и может стартовать **сразу**, на текущих номерах клиента.
2. На пилоте номеров, скорее всего, мало (1–5) → полноценная «ротация пула» там не тестируется; тестируются **ядро продукта** (кампании, автодозвон, статусы, журнал, при необходимости бот и перевод на сотрудника) и **поведение номеров при ограниченных объёмах** (маркировка/«Защитник»).
3. Архитектура с первого дня строится **мультиоператорской**: телефония-адаптер один на всех — сейчас UIS, позже прямые договоры МегаФон/МТС/… подключаются через тот же интерфейс без переделки ядра (см. раздел 3).
4. Полная дорожная карта перестроена на три этапа: **Этап 1 — пилот на существующих номерах → Этап 2 — договоры с операторами → Этап 3 — масштабирование** (раздел 7).


### 1.4. Зафиксированные вводные по пилоту (ответы владельца, 2026-09-05)

1. **Номеров у клиента: 3–5** (МегаФон «Ювис»). На пилоте возможна *частичная* проверка смены исходящего номера (простая ротация по пулу), но полноценные выводы о ротации и репутации — только после Этапа 2 (договоры с операторами).
2. **Доступ к UIS сейчас: софтфон + интеграция в CRM**; наличие SIP-линий / Call API / вебхуков **не подтверждено**. → Первая техническая задача пилота (A0/A1): запрос в UIS и выбор варианта 1/2/3 (раздел 7.1).
3. **Объём пилота: до ~100 звонков/день**, старт 30–50/день, рост ступенями. Этого достаточно для проверки ядра и поведения номеров, но мало для статистики по маркировке — итоговые выводы после Этапа 3.
4. **Цель — конечный продукт, готовый к масштабированию.** Поэтому пилот сразу строится на «взрослой» архитектуре (адаптеры телефонии/CRM, БД с попытками звонков, API v2, события). Масштабирование после пилота = добавление номеров и операторов, а не переделка ядра.
5. **Открытые вопросы, которые не блокируют пилот**: механика «перевода на сотрудника» (A5), сценарий бота-опросника (A6), источник списков и CRM. Они уточняются параллельно (раздел 11).

**Принципы:**
1. **Оркестратор (наше приложение) не держит медиа.** Всю «голосовую грязь» (SIP/RTP/детект ответа/трансфер/подключение ИИ-агента) выполняет медиа-слой (Asterisk/FreeSWITCH или сам UIS через API). Оркестратор управляет: **кого, когда, с какого номера, по какому сценарию, кому передать, что записать в CRM**.
2. **Адаптеры вместо жёстких интеграций.** UIS, CRM, ИИ-агент — за интерфейсами (`telephony.py`, `crm.py`, `agent.py`), чтобы можно было менять провайдеров. Телефония-интерфейс один: исходящий звонок с выбором Caller ID, статусы/события, детект ответа, трансфер. Сейчас реализация — UIS (существующие номера клиента), далее — прямые договоры с операторами (МегаФон, МТС и др.) как дополнительные реализации того же интерфейса.
3. **События + состояние.** Все изменения (попытка, ответ, результат, трансфер) — событиями в БД; UI и CRM подписываются (WebSocket/polling/вебхуки).
4. **Репутация номеров — ресурс.** Никакой модуль не «жжёт» номер: централизованные лимиты, история, «остывание».

## 4. Телефония: варианты и рекомендация

### Вариант A. Оставить GSM-модемы (текущая схема)
+ Уже написано; не зависит от оператора; «свои» SIM = свои номера.
− Мобильные номера маркируются антиспамом быстрее всех (это и есть текущая боль заказчика); звук в линию не гарантирован; 6 линий = потолок; SIM-пул дорогой и неудобный.
**Вердикт: только как стенд/резерв, не как основа.**

### Вариант B. UIS Call API (звонок «из облака»)
UIS даёт Call API: исходящий звонок по клику, интерактивная обработка, вебхуки, Data API, а для интеграций — **данные SIP-линии** [2](https://www.uiscom.ru/producty/integracii/extended-api/), [1](https://www.uiscom.ru/producty/integracii/integracija-s-prostoj-biznes/).
+ Вся телефония на стороне UIS: номера, маршрутизация на сотрудников (софтфоны UIS уже стоят у заказчика!), записи.
− Лимиты Call API (порядка 500 запросов/день, 15/мин — сверх платно) [2](https://www.uiscom.ru/producty/integracii/extended-api/) — для «карусели» на сотни звонков/день тесно; нет медиа для полноценного ИИ-агента и детекта «человек/автоответчик» (только то, что даёт UIS).
**Вердикт: отлично для CRM-клик-ту-колла и перевода на сотрудников UIS; слабо как «диалер под ИИ-агента».**

### Вариант C. Свой медиа-слой (SIP) + SIP-линии/транк UIS (рекомендуется)
Поднимаем Asterisk (или FreeSWITCH) с подключением к UIS по SIP (номерная ёмкость компании), наш оркестратор управляет Asterisk:
- дозвон (originate) с выбором исходящего номера из пула;
- AMD (детект «ответил человек / автоответчик / занято / нет ответа»);
- трансфер на сотрудника: на софтфон UIS/внутренний номер или через SIP REFER;
- подключение ИИ-агента к медиа (мост RTP на ASR/TTS/LLM-конвейер).
+ Полный контроль: пул номеров, лимиты, повторы, ИИ-агент, запись; масштабирование десятками каналов; не привязаны к лимитам Call API.
− Нужен сервер с голосовым стеком (Linux VPS/локальный), настройка SIP с UIS (SIP-линии UIS выдаёт по запросу), больше инженерной работы.
**Вердикт: основа для задач R1–R6.**

### Вариант D. Гибрид (рекомендуемая итоговая схема)
1. **Диалер и ИИ-агент** — через свой медиа-слой (C) на SIP-линиях UIS: карусель, автодозвон, AMD, ротация, бот.
2. **Перевод на сотрудника** — в существующую инфраструктуру UIS (сотрудники сидят в софтфоне UIS): трансфер на внутренний номер.
3. **CRM-интеграция** — двусторонняя: (а) нативный клик-ту-колл UIS в CRM (уже работает у заказчика) остаётся для ручных звонков; (б) наш оркестратор дополнительно пишет/читает CRM через её API (результаты кампаний).
4. Если UIS по каким-то причинам не даёт SIP — fallback: исходящие через Call API (с ограничениями), ИИ-агент через встроенные инструменты UIS/внешнего робота.

> **Открытый вопрос для созвона с UIS:** доступны ли SIP-линии/транк на тарифе заказчика и какова схема выделения дополнительных номеров под пул. От ответа зависит выбор B/C/D.

## 5. Ключевые подсистемы (что строим)

### 5.1. Движок кампаний + автодозвон (R3, R4) — замена нынешней «очереди»
- Сущность **Кампания**: имя, список контактов (из CRM/CSV/вручную), сценарий (шаблон сообщения / ИИ-сценарий / «сразу на сотрудника»), пул номеров, расписание (дни/часы/таймзона), лимиты, максимум попыток.
- **Режимы диаллера**: progressive (операторы свободны → N одновременных звонков), preview (оператор сам запускает следующий), power-обзвон (бот). «Карусель» = авто-прогон списка по кругу с распределением попыток.
- **Автодозвон**: попытки для статусов `busy/no_answer/failed/sent_to_voicemail` — интервал 15–60 мин, до N попыток (например, 3), только в окно времени, «вечером/назавтра» отдельным правилом.
- Часы «не беспокоить» + чёрный список отказов («прошу больше не звонить» — обязательная кнопка/команда бота).

### 5.2. Пул номеров и репутация (R1, R2)
- **Номер** (вместо «линии»): id, значение (E.164), тип (городской/мобильный/8-800), владелец, статус (активен/остывает/заблокирован).
- Выбор Caller ID на каждый звонок: round-robin по пулу + веса (свежие номера звонят чаще), запрет повторного показа того же номера абоненту за N дней, суточный лимит на номер (например, 80–120, настраивается по опыту), авто-«остывание» при превышении.
- **Мониторинг репутации**: считать % успешных ответов/сбросов по номеру; фиксировать жалобы (приходят через бота/оператора: «не звоните»), при пороге жалоб — номер в карантин.
- Интеграция с антиспам-маркировкой: рекомендации ниже (раздел 10) — верификация у оператора, работа с согласиями, снижение интенсивности. Заказчику честно объяснить: **чужие/подставные номера в РФ блокируются («Антифрод»), поэтому «подменка» = легальный пул своих номеров с умной ротацией**.

### 5.3. Детект ответа + перевод на сотрудника (R5) — ACD
- **AMD**: после ответа определить «живой голос / автоответчик / факс» (в Asterisk — приложение AMD или свой анализ, в т.ч. через UIS-статусы при варианте B).
- **Очередь операторов (ACD)**: сотрудники со статусами (свободен/в разговоре/отошёл/на перерыве), приоритеты, максимальное время ожидания абонента.
- **Трансфер**: «горячий» (соединяем абонента с сотрудником, абонент не перезванивает) + **передача контекста**: сотруднику в софтфоне/CRM открывается карточка абонента, история кампании, ответы ИИ-агента.
- Если свободного оператора нет: предложить абоненту «перезвоним в течение N минут» → задача в CRM/очередь перезвонов, или поставить в очередь с музыкой/сообщением.
- **Клик-ту-колл из CRM** для ручных звонков (как сейчас в UIS) — поддержать и для нашего пула (кнопка в CRM → звонок через наш оркестратор).

### 5.4. ИИ-агент (R6) — три уровня, заходить снизу вверх
- **Уровень L1 (быстрый MVP): сценарный бот без LLM.** Разговор по дереву из `scripts.json`: приветствие → вопросы с вариантами («Если интересует X — скажите „да“ или нажмите 1») → распознавание «да/нет/цифра» (ASR по ключевым словам или DTMF) → ветвление → финальный статус. Полностью переиспользует нынешние заготовки `scripts.json`, шаблоны, TTS.
- **Уровень L2: LLM-диалог по промпту-сценарию.** Абонент говорит свободно; ASR → LLM (GigaChat/YandexGPT и т.п.) с системным промптом: «задай критерии: …, при ответе „нет“ на К1 — заверши», → TTS. Результат — структурированный JSON (квалифицирован/нет, ответы на вопросы, теги).
- **Уровень L3: SaaS-голосовой агент** (готовые платформы) — если заказчик хочет «коробку»: подключается по SIP, оркестратор только управляет кампанией и забирает результат.
- Всегда: **запись разговора**, **стенограмма**, **предупреждение «разговор записывается»** (юридически желательно), **правило «стоп по требованию»**, передача «горячего» лида сотруднику (мост L1/L2 → ACD).
- Технологии ASR/TTS: облачные РФ-сервисы (Yandex SpeechKit, VK SaluteSpeech) или on-prem (Vosk) — выбор по бюджету и требованиям к данным (152-ФЗ).

### 5.5. Интеграция с CRM (R8)
- Сначала уточнить, **какая CRM** (Битрикс24 / amoCRM / «Простой бизнес» (UIS-партнёр) / 1С / своя) — от этого зависит адаптер.
- Двусторонний сценарий:
  - из CRM: выгрузка списка обзвона (сделки/контакты + поля), события «нажми позвонить»;
  - в CRM: результат звонка (статус, длительность, запись, теги квалификации, «не звонить»), создание задачи «перезвонить», синхронизация «не дозвонились».
- Если у заказчика уже работает связка «UIS ⇄ CRM» для ручных звонков — не ломать: наш слой пишет в ту же CRM через её API и/или вебхуки UIS.

### 5.6. Данные и хранилище
- Миграция JSON → **SQLite** (потом Postgres, если несколько серверов): таблицы contacts, numbers, campaigns, campaign_items (попытки!), calls, call_attempts, operators, agent_results, recordings, blacklist, consent_log.
- **Журнал попыток** — отдельно от «звонка» (1 звонок = N попыток), текущий `call_log` этого не моделирует.
- Записи разговоров: файлы + ссылки в БД; политика хранения (например, 12 месяцев).

### 5.7. Безопасность (перенести из прошлого анализа, обязательно)
- Закрыть API авторизацией (сейчас `/api/state` и CSV открыты), роли «админ/оператор», смена пароля по умолчанию, HTTPS, токены/сессии.
- Доступ к CRM и UIS — по выделенным ключам, секреты вне кода.

## 7. Этапность работ: пилот на существующих номерах → договоры с операторами → масштабирование

Решение владельца (2026-09-05): **не ждём новых договоров**. Сначала тестируем и доводим продукт на номерах, которые у клиента уже есть (МегаФон «Ювис»/UIS); затем заключаем прямые договоры с операторами-компаниями (МегаФон, МТС и др.) и масштабируемся.

### 7.1. Развилка, определяющая состав пилота (проверить на первой неделе)

Что технически доступно на существующих номерах UIS:
- **Вариант 1 — UIS даёт SIP-линии/транк на существующие номера** (запросить данные SIP у UIS): поднимаем свой медиа-слой (Asterisk) и полноценно тестируем дозвон, детект «человек/автоответчик», ИИ-агента и перевод на сотрудника.
- **Вариант 2 — только UIS Call API / виджеты** (SIP не дают): пилот ограничен — дозвон, статусы, автоповтор, журнал, логирование в CRM; детект ответа, ИИ-агент и горячий трансфер полноценно не тестируются (только то, что умеет UIS). Плюс действуют лимиты Call API (~500 запросов/день).
- **Вариант 3 — гибрид**: исходящие через Call API, а для экспериментов с агентом — временный тестовый SIP-транк.

> **Первый вопрос в UIS: «дайте SIP-линии/транк на текущие номера».** От ответа зависит состав пилота (A5/A6 ниже).

### 7.2. Этап 1 — пилот на существующих номерах (ориентир 4–8 недель)

**Цель:** на реальных звонках доказать, что связка «кампания → дозвон → результат» работает, номера не «сгорают» при разумных объёмах, и получить цифры для go/no-go по масштабированию.

| Задача | Содержание |
|---|---|
| A0. Уточнение | Ответы на чек-лист (раздел 11); часть уже зафиксирована (1.4). Запрос в UIS: SIP-линии на текущие 3–5 номеров, доступ к Call API/вебхукам → выбор варианта 7.1. Уточнение базы (согласия) и механики перевода. |
| A1. Телефония-стенд | Сервер (Linux VPS/локальный), Asterisk, подключение к UIS, тест дозвона «из коробки» с выбором исходящего номера. |
| A2. Ядро | SQLite-схема (кампании/попытки/номера/звонки), REST API v2, авторизация и роли, базовый UI. **Сразу в продакшен-архитектуре** (адаптеры, события) — чтобы после пилота масштабирование было добавлением номеров/операторов, а не переделкой. |
| A3. Диалер-MVP | Кампания из CSV (позже — из CRM), автодозвон (занято/нет ответа → повтор с интервалом), суточные лимиты на номер, «остывание» при превышении. |
| A4. Пилотные кампании | Прогон на согласной базе малыми объёмами (см. 7.5), сбор метрик, контроль жалоб/маркировки. |
| A5. Перевод на сотрудника | (если подтверждена механика и есть SIP) оператор в софтфоне UIS получает звонок с контекстом абонента. |
| A6. ИИ-агент L1 | (опция пилота) сценарный опрос «да/нет/цифра» по `scripts.json`, результат квалификации в журнал/CRM. |

**Правила пилота (чтобы не сжечь боевые номера клиента):**
- база — только контакты с согласием (152-ФЗ); без «холодных» списков;
- объёмы растить ступенями: старт 30–50 зв./день, максимум пилота ~100 зв./день (решение владельца); 200+/день — только после go/no-go и договоров с операторами; следить за маркировкой и жалобами;
- при первых жалобах/«Защитнике» — пауза кампании, разбор, корректировка;
- если клиент может выделить хотя бы один «расходный» номер — использовать его для стресс-тестов.

**Критерии go/no-go на Этап 2:** стабильный дозвон (целевой % уточняется после первого замера), жалоб/блокировок нет или ниже порога, работают автодозвон и (если входило в пилот) перевод/бот, заказчик видит ценность и готов выделять бюджет/номера.

### 7.3. Этап 2 — договоры с операторами (переговоры параллельно пилоту, вступление после go/no-go)

Прямые договоры с операторами-компаниями (МегаФон — продолжение/UIS либо прямой договор, МТС и др.) под нужды обзвона:
1. **Номерная ёмкость под пул** ротации (городские/мобильные; 8-800 — при необходимости).
2. **SIP-транки** (исходящие, при необходимости входящие), SLA, маршрутизация, записи разговоров.
3. **Верификация и антиспам-инструменты оператора** (определение «компания» вместо «спам», работа с жалобами) — это часть решения проблемы «Защитника».
4. Юридические условия автодозвона и работы с ПДн (юрист).
**Почему несколько операторов:** распределение нагрузки и рисков маркировки, разная статистика блокировок, резервирование каналов.
**Что подготовить к переговорам:** результаты пилота (объёмы, дозвон, жалобы), прогноз нагрузки (звонков/день), требования к SIP/API, юридическую базу согласий.

### 7.4. Этап 3 — масштабирование и продакшен (после договоров, ориентир 2–4 месяца)

- Полный **пул номеров и ротация Caller ID** (раздел 5.2): лимиты/день, «остывание», карантин по жалобам, чёрный список отказов.
- Продакшен-диалер: кампании из CRM, расписания, приоритеты, многоканальность, отчёты.
- **ИИ-агент L2** (LLM-диалог: ASR → LLM → TTS), записи и стенограммы.
- **ACD** для всех кампаний (перевод на сотрудника), клик-ту-колл из CRM.
- Полная **CRM-интеграция** (результаты, задачи «перезвонить», «не звонить»).
- Входящие и перезвоны — опция на отдельном «стабильном» номере (не в фокусе).
- Нагрузочные испытания на целевых объёмах; мониторинг репутации номеров.

### 7.5. Ориентиры по срокам и объёмам

| Что | Ориентир |
|---|---|
| A0 + запрос SIP в UIS | 1–2 недели |
| Пилот A1–A4 | 3–5 недель |
| A5/A6 (перевод/бот) — опции пилота | +1–2 недели |
| Итоги пилота, go/no-go | 1 неделя |
| Договоры с операторами (внешний фактор, вести параллельно) | 2–6 недель |
| Этап 3 (масштабирование) | 2–4 месяца |
| Пилотные объёмы | 30–100 звонков/день (старт 30–50, ступенчато), всего ~1–2 тыс. за пилот |
| Рабочие объёмы после Этапа 2 | от 500–1000 зв./день (согласовывается с оператором) |

> После пилота сроки и состав Этапа 3 пересматриваются по фактам (дозвон, маркировка, условия UIS/операторов).

## 9. Состав MVP (что заказчик получает первым)

> MVP = проверяемый на пилоте результат Этапа 1. Полноценные пул номеров/ротация и ИИ-агент — после Этапа 2 (договоры с операторами). Состав ниже — целевой; на пилоте объёмы и пункты про пул/ИИ зависят от доступа к SIP UIS.

1. Кампания обзвона из CRM/CSV: запуск/пауза/стоп, расписание, статусы в реальном времени.
2. Автодозвон (занято/нет ответа → повтор) с лимитами.
3. Пул из 3–10 номеров с ротацией Caller ID и суточными лимитами (решение проблемы «сожжённого номера»).
4. Дозвон через телефонию UIS (SIP), звук гарантирован.
5. Детект «ответил человек»; перевод на сотрудника (если подтвердится механика) с карточкой абонента.
6. ИИ-агент L1 (сценарный бот с квалификационными вопросами), затем L2.
7. Журнал + записи + отчёты; запись результата в CRM.

## 10. Риски и ограничения (важно обсудить с заказчиком)

### 10.1. «Подмена номеров» — юридический и технический предел
- В РФ операторы обязаны передавать номер звонящего **в неизменном виде**; звонки с подменных (чужих/невыделенных) номеров блокируются на уровне операторов, работает система **«Антифрод»** РКН, ответственность — ст. 13.2.1 КоАП и 126-ФЗ [1](https://www.interfax.ru/russia/772580), [3](https://tass.ru/ekonomika/19385225).
- Поэтому **«подменка» реализуется как ротация пула номеров, официально выделенных компании (UIS/МегаФон)**, а не как подстановка произвольных номеров. Чужие номера = блокировки, штрафы, репутационный вред и риск для самого заказчика (его могут счесть спамером/мошенником).
- **Борьба с «Защитником» у абонентов** — это не только смена номера, но и: снижение интенсивности (маркировка срабатывает на массовость и жалобы), качество базы (только согласившиеся), верификация номеров у оператора (определение «компания», а не «спам»), работа с жалобами (чёрный список «не звонить»), короткие/городские номера где уместно. Часть мер — на стороне UIS/оператора, уточнить их инструменты.

### 10.2. Технические
- UIS: доступность SIP-линий/транка и лимиты Call API (500/день, 15/мин) [2](https://www.uiscom.ru/producty/integracii/extended-api/). Если SIP недоступен — план Фаз 2–4 меняется (ограничения по объёму и ИИ-агенту).
- Качество мобильной маркировки в РФ меняется; показатели дозвона нужно мерить на пилоте, а не обещать.
- ИИ-агент: распознавание речи по телефону (шум, акценты) — качество подтверждается только на реальных звонках.
- Записи разговоров и ПДн: хранение в РФ (152-ФЗ), доступ только уполномоченных.

### 10.3. Процессные
- Заказчик описывает продукт словами «подменка/карусель» — нужна фиксация терминов в ТЗ (раздел 11), чтобы не было разночтений на приёмке.
- Интеграция в CRM: доступы и права API; если CRM «закрытая», сроки сдвигаются.


### 10.4. Риски этапности «пилот на существующих номерах → договоры с операторами»
- **Сжечь боевые номера клиента на пилоте.** Номеров мало, и они рабочие. Правила: только согласная база, ступенчатый рост объёмов, пауза при первых жалобах/маркировке, по возможности отдельный «расходный» номер для стресс-тестов.
- **UIS не даст SIP на текущем тарифе** → пилот урезается до варианта 2/3 (раздел 7.1) и лимитов Call API (~500 запросов/день). Проверку делать на первой неделе, чтобы успеть перепланировать.
- **Затягивание договоров с операторами** → разрыв между пилотом и масштабированием. Смягчение: вести переговоры параллельно пилоту, заранее готовить пакет результатов и требований (7.3).
- **Эффект малой выборки**: на пилоте нельзя достоверно оценить долгосрочную маркировку номеров — финальные выводы только после Этапа 3 на больших объёмах; заложить это в ожидания заказчика.

## 12. Итоговая рекомендация

1. **Не «дорабатывать» текущий проект точечно под эти слова** — это другой класс продукта (платформа исходящих кампаний с ИИ), хотя текущий код даёт хорошую отправную точку по бизнес-логике (согласия, шаблоны, журнал, статусы).
2. **Этап 1 — пилот на существующих номерах** (раздел 7.2): стартуем сразу. Первым делом — запрос SIP-линий в UIS; далее минимальный диалер (кампания + автодозвон + лимиты на номер) и тест на согласной базе малыми объёмами.
3. **Этап 2 — договоры с операторами** (МегаФон, МТС и др.) вести параллельно пилоту: номерной пул под ротацию, SIP-транки, верификация/антиспам-инструменты. Масштабирование — только после go/no-go по пилоту.
4. **ИИ-агент**: на пилоте — опционально сценарный бот-опросник L1 (A6); полноценный LLM-агент L2 — отдельным этапом на Этапе 3.
5. Параллельно закрыть **безопасность** (авторизация API, роли, HTTPS) — это требование, а не опция, раз система будет работать с CRM и персональными данными.
